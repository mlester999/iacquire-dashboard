Last updated: 2026-10-26 (evening), on `integrate/phases-3-7-workforce`. This replaces the 2026-10-25 version, which mapped journeys to *existing module tests by file name* and said plainly that the counts were "a map to look at, not proof of quality". Each journey now has a test of its own that follows the process **across services**, with the external systems it necessarily meets named in `tests/journeys/simulations.ts` and proven to be stand-ins.

That registry is the honest half of this document: every entry says which outside system a journey would otherwise reach, which seam stands in for it, and `real: false`. `tests/journeys/journeys.test.ts` fails if an entry claims `real: true`, if a journey has no entry, or if a named seam is not a file in this repository. **No journey has met a real provider, a real phone system, a real social platform or a real model**, and nothing here is deployed.

## What the journeys found

Writing them exposed four things that module tests could not see. None was a crash; all are recorded rather than papered over.

1. **The Lead Sources report counts contacts, not captured leads.** `attributionReport` counts every contact created in the period, and the website chat creates a contact on a visitor's first message, so an anonymous visitor who never fills the form is already a "lead" with a campaign as its source. Journey 2 asserts the consenting visitor is counted and the refused form creates nothing, and does **not** claim the report means "captured leads". This is a product decision for the founder, not a defect fixed here.
2. **A purchase-provisioned workspace is `invited` with no members**, and provisioning requires an active verified owner with completed onboarding. The six employees exist, enabled, in "Setup required" — but no provisioning job opens until the buyer accepts the invitation. Journey 1 asserts exactly that and does not claim provisioning was requested.
3. **Lapse ordering in Automation Studio**: once the sweeper has paused a workflow, a manual start returns `conflict` (turn it on first) before the entitlement check, so `plan_required` appears while the workflow is still active and `conflict` after. Journey 4 asserts both states rather than one guess.
4. **Verified revenue deliberately excludes the in-process simulated provider and every test-mode payment** (`src/lib/invoices/revenue.ts`), and a test-mode account may not pay a real invoice. Journey 6 therefore pays through a live-mode PayMongo seam with a hand-written signed notice; this is the product's rule working, not a workaround to hide.

A test-helper gap found on the way is closed: `tests/support/support-world.ts` `notificationsFor` declared `severity` without selecting the column, so the first journey 7 test could not assert it. It selects it now, and `journey-7-boundaries` asserts that a quote waiting for the owner is a warning (it needs a decision), not a plain heads-up.

## Open gaps across all eight

1. **No journey has run against a real provider**, and none can without the founder's approvals and accounts (`docs/roadmap/phases-3-to-7/blockers.md`).
2. **The scheduler has never run**, so every scheduled stage (renewal reminders, missed-call follow-ups, social publishing, review requests) is verified only through injected clocks.
3. **Real AI behaviour** (replies, research, drafts) is verified only against simulated models; no live Hermes profile has answered for any client.
4. **The browser pass is separate from these tests.** What was driven in a real browser is recorded in `docs/roadmap/phases-3-to-7/verification-evidence.md`; a passing journey test is not browser evidence, and neither is the reverse.
5. **No journey has been run by a person end to end** in one sitting (buy → onboard → operate → cancel); each is proven in parts.
