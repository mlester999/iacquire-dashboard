## Trust boundary and deployment shape

The public application never receives Docker access, host root, unrestricted SSH, or a filesystem path. It serves two authenticated internal endpoints:

- POST /api/internal/hermes-provisioner/claim leases one eligible job for a single server-pinned gateway.
- POST /api/internal/hermes-provisioner/complete accepts only the matching leased result, then saves a new profile key through the existing Vault-backed credential path.

The worker polls outbound over HTTPS using a dedicated service token. The portal pins that token to one gateway ID. Claiming is disabled unless the gateway is connected, multiplexed, marked restricted-service-verified, has a separate isolation-verification timestamp, and has no mapped iAcquire agency profiles. The isolation timestamp is a privileged operator attestation; no public UI can set it.

The dedicated profile volume contains no iAcquire agency profiles or other agency data. The runtime scan permits only `default` and `c-` profiles that carry a matching ownership marker or interrupted-creation journal bound to the pinned gateway. Tenant, agent, profile, source job and gateway must match on provision and sync. Do not mount the existing `/docker/hermes-agent-wpwm/data` volume. The public application receives no Docker access, host root, filesystem path, Supabase key, or customer messaging credential. The worker itself runs as UID/GID 10000 in a separate container, with a read-only root filesystem, no capabilities, no Docker socket, and no mount of Hermes' provider-secret home. It can write only the client profile and worker-state volumes and make outbound HTTPS requests to iAcquireOS; its Hermes API access uses container loopback. Hermes resolves `/p/<profile>/` against the current named-profile directory on each request. Because the worker has a separate Hermes home, its CLI cannot signal the gateway's control socket; after atomic profile publication and key/config writes, it polls the profile-scoped capabilities route for up to 40 seconds before starting SOUL and inventory checks. This confirms that profile identity and credentials are visible through the shared API listener without restarting the gateway. A timeout leaves the durable journal for safe retry. The gateway's separate adapter reconciliation follows its native rescan lifecycle; no client messaging adapters are configured. The official Hermes supervisor starts as root inside its own confined container to follow the image's s6 startup path; that container is not privileged, has no host PID/network mode, host data bind, or published API port.

Hermes resolves model-provider keys from each profile's own `.env`, so the worker reads one private host-mounted model-provider key file and writes that key only into each owned client profile. It is excluded from job results and audit records. The mounted document accepts exactly one provider API key from a small allowlist; messaging, CRM, customer, Hermes API and internal-agency credentials are rejected. The separate default-profile API key is used only for a read-only startup inventory probe. The service token is also supplied as a private file; the worker rejects ambiguous sources, symlinks, broad permissions and oversized values, removes secret paths from its environment before invoking Hermes CLI, and never logs secret values.

The deployment package is [services/hermes-provisioner/compose.client.yaml](../services/hermes-provisioner/compose.client.yaml), with the [build definition](../services/hermes-provisioner/Dockerfile) and [deployment/recovery runbook](../services/hermes-provisioner/DEPLOYMENT.md). The worker Compose profile is off by default. Before the worker process creates audit/heartbeat state or polls the portal, it authenticates to the client-only default profile and requires two stable reads of the native challenged catalog contract, including `complete=true`, exact provenance and the matching challenge echo. It does not accept the upstream resolver response as a substitute. If the route or required provenance is missing, it exits before any queue claim or profile write. The individual named profile is still verified with its own key after creation/sync. The package publishes no Hermes port; an approved Cloudflare Tunnel can reach the private Docker network, while the portal's Cloudflare Access service-token check remains in place. A new hostname must be approved as an exact `INTEGRATION_ALLOWED_HOSTS` entry before gateway registration.

The current mixed-use container cannot host this worker. A distinct client-only runtime, its service authentication and a compatible Hermes build remain prerequisites for deployment. The compatible candidate has now passed isolated acceptance; no Hostinger installation or production profile creation was performed.

## Worker transaction

1. Validate the HTTPS portal origin, dedicated service token, pinned gateway ID, non-root UID, Hermes CLI and its installed profile-create flags. Reject an unsafe Hermes home, agency profile namespace, symlink, stale lease, invalid role, path-like profile name or unknown manifest field.
2. Accept only the six known roles and the stable c- tenant namespace. The server derives the profile name from the tenant slug digest and role. The manifest contains an applied configuration version, approved compiled instructions, fixed tool policy, SOUL/config digests, tenant/agent IDs and lease expiry; it contains no shell command or filesystem path.
3. For a new profile, call Hermes CLI with a fixed argv: profile create, --description, --no-alias and --no-skills. A durable intent record is written first. The per-profile Hermes API key is generated by a CSPRNG and written to that profile's `.env` with mode 0600. The one approved client-only model-provider API key is written there too. The worker does not set `API_SERVER_ENABLED` in named profiles; Hermes' default profile owns the single API listener, and each named profile's key scopes its `/p/<profile>` API route. Neither credential is written to the job marker, callback detail or audit; only the Hermes profile key is returned after all host checks pass so iAcquireOS can save it to Vault.
4. Merge only the model block from the client-only Hermes home's blank profile. Reject secret-looking fields. Apply the server-generated client tool policy, disabled toolsets and containerized terminal settings. Write SOUL.md and config.yaml by atomic replacement with fsync and safe path checks.
5. Before publishing the result, temporarily disable API tools and run a one-use canary with a random marker embedded only in the SOUL. The worker authenticates the profile route, verifies its primary model identity, confirms no canary tool event occurred and requires the exact marker output. A new session avoids reusing an older cached prompt. It then writes the final reviewed tool policy and verifies the profile's full challenged runtime tool inventory.
6. Return only hashes, profile identity, inventory evidence and the newly created API key. The application compares the lease and stored manifest digests, writes the credential to Vault, maps the client employee to the pinned gateway and marks the job awaiting portal health verification. The independent portal health check must still pass before the employee can run.

Configuration sync jobs are created only for profiles bearing a successful restricted-provisioner ownership record. Each sync names the originating provision job and applied config version. The worker refuses a missing or mismatched ownership marker, does not replace the key and atomically applies the newly approved SOUL and tool policy. The agent's recorded host config version must equal its active iAcquireOS config version before health or run gates can open.

Retries are idempotent. A local intent journal lets the worker resume its own interrupted blank creation. A pre-existing unmarked profile, conflicting tenant marker, malformed key or symlink is a hard failure and is never adopted. Expired leases can be reclaimed up to three attempts with backoff. Replays after a committed callback verify the existing credential fingerprint and result reference instead of creating another Vault entry. Recovery never prints or copies a key into logs.

Audit records are durable JSONL under the private worker state directory, mode 0600. They include tenant/agent/job IDs, profile name, role, pinned gateway, Hermes version, config version, SOUL/policy/effective-config hashes, stable inventory digest and safe outcome code. They exclude the API key, lease token, SOUL text, manifest body and client business content. Appending is fsynced and fail-closed; a missing/full/unwritable audit log prevents a success callback. The job table stores only hashes and source references.
