# Decisions

## D1. Website chat is a conversation channel of the Unified Inbox, not a parallel system (Phase 3)

`conversations.channel` gains `web_chat`. The shared provider `Channel` type (sms, whatsapp, email), `messaging_channels`, consent events, suppressions and templates do not change: a web chat reply is stored as a `conversation_messages` row (provider `web_chat`) and delivered to the open widget, never sent through a provider. This gives website chat the Inbox, takeover, pause, ownership fence, escalation, CRM context and lead-scoring events without touching the send chain that 124 files depend on. The cost is a `ConversationChannel` type for conversation rows, a branch at the top of `queueOutbound` (`queueWebChatOutbound`, which keeps the ownership fence, pause, escalation-pending check and automation gate), and a refusal in `evaluateSend`.

## D2. A web visitor is never merged into an existing contact

A visitor can type any email address or phone number. Matching it to an existing contact would let a stranger attach their conversation (and read the AI's context, which includes that contact's confirmed facts) to someone else's record. Chat sessions therefore get their own contact; an exact match with an existing contact is recorded as `possible_match_contact_id` for a person to review and merge with the existing merge tool. The Inbox shows that as a note with a link; nothing is linked automatically. Details a visitor types are stored as unverified and shown as unverified.

## D3. Tenant identity comes from the widget key plus an Origin allowlist, never the request body (revised)

External sites use a public widget key (`wk_` + 24 characters; not a secret, it names the widget) and the browser's Origin must be on the widget's allowlist (exact hosts, one-level `*.` wildcards; the workspace's own Website Studio hosts are allowed automatically). CORS is echoed only for an allowed origin. Browsers set Origin and cannot forge it; non-browser clients are limited by rate limits (per session, per address, per day), session tokens and the fact that the key grants only the visitor chat surface of one workspace.

**Revised from the first plan.** The first plan served Website Studio sites' chat same-origin (`/__iaq/chat`). The audit found that the site runtime database role `iaq_site_runtime` has no table privileges (by design), so it cannot serve chat. Website Studio sites therefore load the widget from the portal origin like any other site: the site's CSP `connect-src` gets only the portal origin, a nonce'd `<script>` is injected in `site-runtime/[host]/p/[[...path]]/page.tsx`, and the runtime role may call exactly one security-definer function, `app.site_chat_widget(p_host)`, which returns the public key for a verified host with a live publication whose workspace turned the chat on.

## D4. Attribution never invents

Touches record only what the visit carried (UTM, click ids, landing page, referrer) or an authorized person's manual choice, and say which (`known`, `inferred`, `unknown`). The classification precedence is manual, UTM, paid click id, referrer (inferred), channel for a phone call (inferred), unknown, and "direct" is never a result. The touch history is append-only; the first and latest pointers are recomputed from it, so a touch that arrives late but happened earlier becomes the first touch. Revenue is never shown: won deal value is labelled as deal value (verified revenue needs Phase 5 payments). Cost per lead needs a manually entered cost wholly inside the period and a single currency; return on spend needs verified revenue and a cost above zero, and says what is missing otherwise.

## D5. No new AI Employee identities

Website chat is answered by the conversation's AI employee (default `sales_assistant`; the Appointment Setter is selectable and reachable by handoff). No "website assistant" employee exists. The widget's `ai_enabled` switch is the autopilot authorization for the channel.

## D6. The visitor-facing AI sees only what the owner ticked

The generator receives only the company-knowledge sections selected for the widget, approved and not risk-flagged. A price is blocked unless it appears in the approved prices (`ungroundedAmounts`); instruction-leak text is blocked; the visitor's text is wrapped in a delimited block; failures become an internal note, an escalation and a visitor-visible system message. The real language model has never been evaluated against this prompt (only stubs and the simulated QA model), and that is stated everywhere it matters.

## D7. Visitor session tokens

An opaque 32-byte token, stored only as a sha256 hash, sent as a Bearer header, kept in `localStorage` only after the first message (so a visitor who never writes leaves nothing behind). The visitor's address is stored only as a keyed hash for rate limiting.

## D8. Retention and erasure are part of the feature

A daily job (`webChatRetention`) deletes anonymous chats after `anonymous_retention_days` and others after `retention_days`, and removes the chat-made contact only when it is still empty. `redactContact` also erases the contact's chat sessions and attribution touches.

## D9. Source names are stored normalized and read back readably

Stored source names are lower case with hyphens. The display label raises the first letter and reads hyphens as spaces ("trade-show" shows as "Trade show"); typing that label back stores the same name, so a label and its stored name never drift apart.

## D10. QA findings are fixed where they are found, including in Phase 1 and 2 code that the new feature exposes

Two small fixes landed in the Inbox thread. The scrollable message log was not keyboard-focusable (a gap already present in Phase 1; axe flagged it). System-authored messages were labelled "Teammate"; website chat adds system notices to the thread (for example "I've asked a team member to join"), so they now read "Automatic notice". One shell issue was found and left alone: the sidebar's AI-employee links have an accessible name that does not contain their visible text (axe `label-content-name-mismatch`, six or seven nodes on every portal page); it is not part of this work and is listed in `blockers.md`.

# Phase 4: AI social media manager

## D11. Meta first, behind an adapter, with a simulated twin that production refuses

Facebook Pages and Instagram professional accounts (reached through their linked Page) are the only providers. Every provider call goes through one adapter interface (`providers/types.ts`): `meta` talks to the Graph API, `simulated` is an in-process platform used by tests and browser QA and is refused in production (`simulatedAllowed`). The Meta adapter has only ever run against a replaced HTTP layer; endpoint and permission names must be re-read against Meta's current documentation before the app is submitted for review (stated in `meta.ts` and `meta-oauth.ts`). A future provider is another adapter; none is claimed.

## D12. An approval is of an exact version, and nothing the person did not read can go out

`social_posts.version` bumps on every change to what will be posted; an approval stores `approved_version`; a scheduled post must have `approved_version = version`. Any edit to caption, hashtags, link, media or account voids it and returns the post to draft. AI drafts (origin `ai`) always need a person's approval, whatever the settings (`approval_for_publishers` only adds a second person for people who could publish anyway), and a duplicate of an AI draft stays an AI draft. Approve belongs to the client's owner and admin; the agency never approves what a client publishes. Every approval, edit, schedule, cancel, retry and publication is a row in `social_post_events` with its actor.

## D13. Publishing is a leased, resumable, idempotent job with two write switches

One live job per post (partial unique index), an idempotency key of post:version:instant, a lease a restarted worker takes over, and `state` that records each provider step (container created, publish sent, provider post id, done) so a resumed job continues instead of repeating. A lost answer becomes `needs_reconciliation`: the publisher asks the platform whether the post exists before anything is re-sent, and a person resolves what it cannot decide. Real publishing needs both the environment switch `META_SOCIAL_WRITES_ENABLED` and an account whose adapter is `meta`; the scheduler jobs are off in production until their stage is started. A job also checks the workspace gate (`org-gate.ts`, the platform's outbound-automation rule) so a suspended, paused or shut-down client's posts stop. A post more than six hours past its time when first claimed is not sent (D20), so switching publishing on later never posts stale content.

## D14. Credentials are sealed server-side and never readable by the application role

Account credentials are AES-GCM sealed JSON in `social_accounts.credentials`, a column the application role has no grant on (column-level grant list in 0089); the sign-in state table is server-only (no grant at all) and holds the encrypted Page choices for ten minutes only. Nothing sealed is returned to a browser, a server-action result, an audit row or a log. Deauthorize and data-deletion callbacks verify Meta's signed request (HMAC-SHA256, constant time) and revoke by provider user.

## D15. Honest connection states and what stops publishing

`connected`, `needs_reauth`, `error`, `revoked`, `disconnected`. Disconnect, revoke and needs-reauth cancel queued jobs and fail the affected scheduled posts with a plain message ("Reconnect it and schedule it again"); a post whose outcome is unknown stays flagged for a person. A transient health failure does not change an account's state (review finding). Reconnecting a Page moves its unfinished posts to the new connection.

## D16. Media: managed storage with a cap, client drives as an honest "not available"

Uploads go to the private bucket `social-media` through the existing private-file service; reading needs `social.view`, writing `social.create`. Only managed-plan workspaces may upload, and managed storage is not unlimited: a per-workspace cap (default 2048 MB, `SOCIAL_MEDIA_STORAGE_MB`; the default is a proposal the founder must confirm). Google Drive and OneDrive appear as "not available yet" because no OAuth app exists. Files are validated by content (magic bytes, dimensions, EXIF orientation) and per platform (Instagram: JPEG, 4:5 to 1.91:1).

## D17. AI help is a user-invoked drafting helper, not a seventh employee

Ideas and captions are generated from approved, non-risk-flagged company knowledge only, tone and brand-voice note included, and the output is filtered for invented prices, percentages, offers, testimonials and statistics. Every result is a normal editable draft. It is not an AI Employee: no employee identity, tool or memory is involved. The only employee involvement is the Performance Analyst's read-only social review (failed or unconfirmed posts, approval backlog, accounts needing reconnection, and engagement or campaign patterns only where enough returned numbers exist). A dedicated social-media specialist employee is a possible future product decision and is not created here.

## D18. Analytics show only what the platform returned, and leads are tied to a post only by evidence

A metric the platform did not return is absent, never zero. Reach, impressions and clicks are not collected (insight permissions are not requested). A lead is tied to a post only when its own recorded visit (a Phase 3 `lead_touches` row) carried the post's tracking code in `utm_content`, and an outcome counts only if it happened after that visit. Posts that cannot carry a code (no link, links off, Instagram captions) read "Not tracked". Likes and views are never described as sales.

## D19. Social media belongs to the client workspace

Accounts, approvals and publishing are the client's; the section is hidden from and refused in agency workspaces. An agency-side surface for working inside a client's calendar is a possible later task.

## D20. Decisions taken after the Phase 4 review (summary of the fix brief)

* Overdue posts: more than six hours late at first claim means "not sent" with a notice (one constant).
* Links: https only, case-insensitive in the database, scheme lower-cased, validated before any write.
* A tracked link always carries its own code in `utm_content`.
* Token expiry: a warning to owners and admins seven days before a token or data-access expiry.
* AI helper: per-user hourly and per-workspace daily rate limits.
* Failure notifications and automation events are keyed per failed job, so a retry that fails again is announced again.

# Phase 5 Wave 1: decisions taken after the adversarial review (2026-10-24)

The review of proposals and signing, customer invoices and payments, reputation, AI metering and the consent rule for visitor-typed details found 43 defects. These are the decisions that shape what was built to fix them; the number in brackets is the one in the fix brief. The module documents say what the code does ([../../proposals.md](../../proposals.md), [../../invoices-and-payments.md](../../invoices-and-payments.md), [../../esignature.md](../../esignature.md), [../../voice-and-reviews.md](../../voice-and-reviews.md), [../../production-scheduler.md](../../production-scheduler.md)).

## D21. A closed dispute never restores money on a guess (fix brief D1)

The closing event carries an outcome. Won restores the payment; lost first records a refund with the source `chargeback` for the disputed amount, and the payment and invoice follow what the rows add up to; unknown or missing keeps the payment disputed, tells the owners and managers and shows it on the invoice. An owner can also open and close a dispute by hand (`invoices.refund`), which is the only way to represent a reversal that is never followed by a resolution. Why: the review (#3 and #5, both high) found that closing a dispute always put the payment back as received money whatever the outcome, so a lost dispute would still count as revenue; and the PayMongo adapter normalises no dispute event at all, so a chargeback on a PHP payment had no representation. Nothing financial changes on a guess (D43).

## D22. A test payment belongs to a test invoice (fix brief D2)

Test-mode payments are recorded only on an invoice made on purpose as a test invoice (`customer_invoices.is_test`, in the unreleased `0093`); a test invoice is labelled everywhere, never reminded and never counted in receivables, overdue, verified revenue or the deal rule. A real invoice never gets a test payment. Built in `0093`: the mark is the owner's alone and fixed once the invoice leaves draft, the database refuses a test-mode payment on a real invoice and a live or hand-recorded payment on a test invoice, and a test invoice has its own `TEST-` numbers. Why: the go-live gate needs a provider-confirmed test payment on some invoice, and the first build let "Pay as a test" mark a real customer invoice permanently paid with no way back (#16). Marking is the owner's alone and the numbering is separate (D45).

## D23. A PayPal delivery while real provider calls are off is refused, not stored (fix brief D3)

The route answers 503 with Retry-After before any outbound call and stores nothing; PayPal sends it again, and the scheduled read-back of open checkouts records the payment once `CUSTOMER_PAYMENTS_WRITES_ENABLED` is on. A PayMongo delivery is still recorded, because its signature is checked locally. Why: PayPal verifies a delivery by calling PayPal with the business's credentials, which is a real provider call; the review (#27) found it happened while real calls were off. Refusing with 503 keeps the rule literal and relies on PayPal sending the event again (its retry window is a guess).

## D24. Agency read of proposal documents needs a support session; the proposal tables stay as built (fix brief D4)

The `proposal-documents` bucket requires an active support session for an agency caller (`app.file_permission`, migration `0090`). The proposal tables keep the `proposals.view` read policy, which does not: **a founder decision still open** (recorded in the header of `0091_proposals.sql` and the `proposals.view` note in `src/lib/permissions.ts`). No screen shows an agency person those records today. Why: the review (#22) found assigned agency staff could read proposals, signing records and the stored documents with no audited support session; the fix brief closed the stored documents (which hold the full proposals and signed copies) and recorded the tables as an open founder question instead of changing their read policy, which 0091 copied from the social tables (the agency roles hold the view permission there too).

## D25. The "typed by a visitor" fact belongs to the address and to the consent event (fix brief D5)

A merge never turns an unverified typed address, or the consent ticked with it, into a verified-looking one. The send rule reads the identity (`contact_identities.typed_by_visitor`, `verified`, `verified_via`), not the contact's `created_via`. Why: the review (#1 and #2, both high) found a contact merge made a visitor-typed address and its promotional consent look verified, so the first build's contact-level rule was defeated by an ordinary merge. The column is `typed_by_visitor` on `contact_identities`, added in the unreleased 0087 (D55) because no existing column could carry the fact.

## D26. A public survey answer is attributed only through a verified identity (fix brief D6)

An answer that matches an existing customer only by a typed email or phone is stored unattributed, with the possible match kept for staff, and triggers nothing about that customer until a person confirms the match. A match to a verified identity attributes as before. Why: the review (#19) showed anyone could attach a fabricated low rating to a real customer, and stop that customer's retention messages, by typing the customer's email into a public survey form.

## D27. Holds and suspensions reach what is already queued (fix brief D7)

A person's hold on automatic messages withdraws already queued automatic review asks and invoice reminders in the same transaction and is checked again when the dispatcher sends. A suspended or archived workspace's queued review-batch messages are held (the batch job considers every workspace and lets its own gate park them), and system sends of scope retention and billing are gated on the workspace being allowed to send at dispatch (scope retention by the dispatcher's own gate, `src/server/messaging/dispatch-gate.ts`, which re-checks every 5 minutes; scope billing by `evaluateSend` itself, at queue time and again at dispatch). Why: the review found review messages already queued still went out after a workspace was suspended (#9), and a person's hold on a customer stopped new automatic asks but not the ones already waiting (#10).

## D28. Messages waiting for a sending window count against a batch's pace (fix brief D8)

Releasing the window never releases more than the approved pace per minute. Why: the owner approved a pace (D48); the review (#11) found that messages queued while the sending window was closed all carried the same send time and, when the window opened, left at about 25 a minute (the dispatcher's limit per tick) instead of the approved pace, because the pace bounded only how fast messages were queued.

## D29. Every `llmComplete` caller is metered or exempt, and only the callers named below check the workspace first (fix brief D9)

The decision asked that lead scoring and every model call check the workspace is active and has credit before calling. What was built is narrower, and the first text of this entry said "every" (corrected on 2026-10-24 against the code, `src/server/llm/gate.ts` and its callers):

* Every file that imports `llmComplete` meters its calls (`meterModelUse` or `recordModelUse`), or is on a three-entry exemption list with a reason (the two AQi files, which keep their own accounting, and the integration health ping, which has no workspace to charge); a source-scan test (`tests/llm-callers-metered.test.ts`) fails for a new caller that does neither.
* Lead scoring checks that the workspace is active, not paused for workflows, and has credit (`modelGate`), before the model and before the daily allowance is taken; otherwise the rules alone score.
* The Website Studio assistant and the employee generator check the workspace is active but **not** credit: a new workspace has no credit during setup, so a credit gate would stop setup-time AI for every new workspace. `credit: false` becomes `credit: true` in the gate call if the founder wants otherwise.
* The support AI, the help assistant and the Inbox AI check neither status nor credit; social, proposal and reply drafting check credit but not status. Not applied (each needs its own honest refusal and test); the calls are started by a person, so the exposure is small.
* The web chat reply check runs the shared claim check and covers singular currency words, every supported currency code and P/Php prefixes; the published token rate is entered and labelled per 1,000 tokens.
* Not covered by the scan or the meter, per stage D1's report: calls that do not go through the metered `llmComplete` path (the streaming callers: the AQi answers, which keep their own accounting, and the Automation Studio builder) and the Hermes customer-reply path, which still records nothing when no `llm` rate is published. "Every model call" in the fix brief was wider than this.

## D30. Reconnecting a review location adopts what is there; a reply permission error switches off replies only (fix brief D10)

Reconnecting the same location adopts the old mirror rows and replies and replaces the credentials in place. The Facebook sign-in can ask for the review permissions as an option, `canReply` comes from the Page's granted scopes, and a permission error while posting marks the reply failed and turns `can_reply` off without marking the connection as needing to be reconnected. Why: the review found a Google connection that needed reconnecting could not be reconnected (#20), disconnecting and reconnecting the same site duplicated every review and reply (#21), the Facebook review connection needed a permission the Social connect flow never asks for (#26), and one permission error while replying marked the whole connection broken (#37).

## D31. The public pages have their own emergency stops (fix brief D11)

`PROPOSALS_PUBLIC_DISABLED`, `INVOICES_PUBLIC_DISABLED` and `REVIEWS_PUBLIC_DISABLED`, all off by default: the customer's page and its routes answer "temporarily unavailable" before any database read. Each leaves alone what it should not stop (money that arrives, the team's own screens, requests and reminders already sent); the table is in [../../production-scheduler.md](../../production-scheduler.md). Why: the plan promised every public page and webhook an environment kill switch; the requirement mapper found only the proposal page and the website chat had one (new work N3 in the browser QA notes).

## D32. Money is integer minor units, exponent-aware, in eight currencies (fix brief D12)

Amounts are integers in a currency's minor unit (`src/lib/money`: per-currency exponent, BigInt intermediates, one rounding per line, a total is the sum of rounded lines, never a floating point number). Columns are named `*_minor` and are bigint, always selected as text and parsed because PGlite returns bigint as a number and the hosted driver as text. The eight currencies USD, PHP, EUR, GBP, AUD, CAD, SGD and JPY are enforced by database checks, so adding one needs a migration. Currencies are never added together or converted; one-time, monthly and yearly amounts are totalled apart. Why: the audit had a two-decimal-only whitelist and `*_cents`, which would be wrong for JPY and would break when the money library became exponent-aware. **Status:** engineering; founder confirms the eight are the launch list and that clients type their own exclusive tax rates (the platform gives no tax advice).

# Phase 5 Wave 1: decisions taken while building and fixing (D33 to D55) and after the browser QA (D56, D57)

These are the deviations from the audits and the build and fix stages' choices that are really decisions, as the stage reports recorded them (a few, such as D33 and D45, took their final shape in the fix wave). All were taken by engineering (the stage implementers, checked by the lead); none was approved by the founder. Each entry ends with what the founder or counsel still has to confirm. The smaller deviations (names, defaults of no consequence) are in `phase-5-wave1-checkpoint.md`, section 8.

## D33. Every Wave 1 module is dormant until a Super Admin switches it on, on one page

One `org_features` row per workspace and module, absent means off: `proposals`, `esign` (needs `proposals`), `invoices` (customer payments need it), `reputation_surveys`, `reputation_batches`, `reputation_reviews`. The page `/admin/module-rollout` lists client workspaces only (suspended ones with a badge), shows what each key unlocks and what it still needs (a connection, an environment switch, a scheduler job, an owner authorization), and what happens to customers when it is switched off; every change is a confirmed, audited action that calls the module's own service (`setOrgFeature`, `setInvoicesEnabled`, `setSurveysEnabled`, `setBatchesEnabled`, `setExternalReviewsEnabled`) and never writes the table itself; only the agency Super Admin. Why: the hard rule is that new features are dormant, the audits promised "one entitlement seam" per module, and the review found that nothing in the product could flip any of them. Switching a module on connects nothing and sends nothing. **Status:** engineering; founder decides who may flip a switch in practice and where each module sits relative to the US$1,499 implementation and the US$299 monthly plan (no price is coded).

## D34. Proposal approval defaults

Approval is required for an AI draft always (not switchable), for an author who can write but not send, for a discount or a price below the price book (the owner may turn that rule off), and above an amount the owner sets (one number, typed in the default currency, compared as a plain number with every proposal's total whatever its currency); the two-person rule (the author or submitter cannot approve) is off; AI drafting is off; a sales rep may send their own proposal without a second look when no rule applies, and may edit or send only their own work unless owner or admin. Tasks are created when a proposal is accepted and when changes are requested (not on decline or expiry). The optional CRM effects (tag on send, stage on send, won-stage on accept) are off until the owner turns them on. Why: nothing is invented for the client and the audit's text on tasks was ambiguous. **Status:** engineering defaults; founder confirms the approval defaults, the follow-up tasks, and whether the approval-over amount should be per currency.

## D35. The customer's link, code and session

The link's token is derived from a server key and only its sha256 is stored, so staff can be shown the address again on request (`getShareUrl`, `renewShareLink`, only to someone who can send) and a database read never yields it; it is never in a proposal's detail, event, audit row, notification, message body, log or export. The page is served with `Referrer-Policy: no-referrer`, no-store and noindex. Answering needs an emailed one-time code sent only to the address on file (6 digits, 10 minutes, 5 tries, 60 seconds between codes, 5 an hour per link and 10 an hour per address, only a keyed hash stored); the session cookie is HttpOnly and SameSite Lax, slides for 30 minutes and ends after 8 hours; a link lives 90 days, or 30 days past a valid-until date (400 at most); 5 requests for changes a day; an expiry warning 2 days ahead; 120 requests a minute per address. The customer's email address is masked on the page and not printed in the PDF. **Sending does not email the customer:** the team copies the link into its own email or message (copy-link first). Why: a bearer link is a credential; sending through the consent chain needs counsel's wording for a first delivery. **Status:** engineering; **every number above is a proposal** the founder confirms, together with whether the code should be required just to view or download, and whether the code email may come from the platform's sending address with the business's name in the text (Resend's SPF and DKIM must cover it). The rotating-key limit applies: without `APP_ENCRYPTION_KEY_PREVIOUS`, staff cannot be shown an old address (a customer who already has it still works).

## D36. The three honest levels of "seen"

*Opened* (the page was requested; a scanner or link preview does the same), *viewed in a browser* (a beacon after 3 seconds visible plus a real interaction; a script-running scanner that also simulates a pointer would still count), *verified* (someone entered the emailed code: they control that mailbox, nothing more). History and labels say exactly that ("the link was requested", never "the customer read it"). `proposal.viewed` fires on the first browser-confirmed view, not on the first code verification (otherwise a customer who only reads would never fire it), and its description says it does not prove anyone read the proposal. The invoice page and the review page follow the same restraint: "opened" counts link opens. **Status:** engineering; no confirmation needed.

## D37. A recorded answer is not an electronic signature

An acceptance on the page is recorded only from a verified session, for the exact frozen version whose hash was shown, once, with the acknowledgement text the customer saw and its version; the decision table is append-only. The page and the PDF say it is a recorded answer, not an electronic signature. An answer a person records for a customer is labelled "Recorded by <name>; not verified by the client". The acknowledgement text (`src/lib/proposals/ack.ts`, version 1) is draft wording for counsel. Why: nothing in the product may call a ticked box, a typed name or an emailed code a signature; only a signing service's verified completion is labelled "Signed through a signing service". **Status:** engineering; **counsel must approve the final text before the module is enabled for a real client.**

## D38. E-signature: the client's own account, believed only on the service's word

Each client connects its own signing account (PandaDoc first and only; no per-document cost reaches iAcquire; the platform-run master account is not built). A request is for one *sent* version, locked to its content fingerprint and the sha256 of its stored PDF; one live request per version (database index); the intent is written before any call that could make a document; a lost answer is checked with the service and never repeated. A signature counts only from a webhook signed with that connection's own key, or a status read with the same key, and is applied only if the proposal is still sent, on that very version, unanswered, in date and intact; otherwise it is kept and set aside with a plain reason. Every way a proposal ends ends the ask (revision, withdrawal, an answer recorded by a person, the valid-until date, the customer declining, a privacy request, disconnecting, closing the workspace). `ESIGN_WRITES_ENABLED` holds back writes only (handing over, withdrawing); key checks and status reads are reads and a working real connection makes them whatever it says. `esignSync` runs on every tick (a five-minute rhythm would stretch one request over 10 minutes or more). Completing a signature does not revoke the customer's link (they see "You signed this proposal through a signing service"). A PandaDoc withdrawal is recorded here and the business is asked to withdraw it in PandaDoc; the certificate is not downloaded; the signature field placement is our own guess at PandaDoc's schema. The stand-in service reaches nothing and is refused in production. **Status:** engineering; founder decides per-client versus master account, the commercial placement, and what counsel allows to be said about enforceability. Everything about PandaDoc is unproven.

## D39. PDF: our own small writer

One deterministic writer in `src/lib/pdf` (no dependency; standard fonts; Latin text; currency shown as a code; US Letter for USD, CAD and PHP, A4 for the rest) behind a renderer seam (`src/server/proposals/documents.ts`). The PDF of the frozen version is stored in `proposal-documents` with its sha256 on the version row (write-once) right after the send commits, because storage cannot join the database transaction; if that fails the send stands, the history says so and each download is rendered on demand from the version, rate limited. The customer PDF prints name and company, not the email address (a PDF stored earlier keeps its bytes until re-made, and a re-made one has a new hash). Invoices use a print page, not a PDF. Why: the plan chose no new dependency, and a PDF is a credential-adjacent file. **Status:** engineering; the appearance of a PDF has not been seen as an image by the build stage.

## D40. AI proposal drafting can only choose and write, never price

The model sees only approved, unflagged knowledge from five sections (business description, products and services, approved pricing, policies, brand voice), the price book, and the customer and deal as fenced untrusted data. Its output has no field for a price, total, discount, tax, date or terms: it names price book items by id with a whole quantity from 1 to 999 and writes a few paragraphs; the server builds every priced line from the price book rows it looks up itself. Every sentence is checked and a failing one is **dropped, never edited** (a placeholder, HTML or link, web address or phone number, a number not in an allowed set by exact whole-number match, an amount written in words, a claim the approved knowledge does not back, a turnaround or refund promise); what was dropped is recorded on the run and shown. Limits: 20 requests an hour per person and 50 a day per workspace, at most 15 items, 45 seconds, 1,800 output tokens, a brief up to 600 characters. The result is always a draft with origin `ai` that needs a person's approval. Off until the owner turns it on. **Status:** engineering; **the limits are proposals**; the real model has never been evaluated against this prompt.

## D41. Invoice defaults and who may do what

Approval and issue are one act: approving is issuing, by someone holding `invoices.approve`, naming the version they read (there is no separate approved status). A creator without `invoices.approve` may issue their own manual draft only when the owner switched `approval_required_for_creators` off; a workflow- or deal-made draft always needs an approver. Defaults offered: number prefix `INV-` with a 4-digit minimum, payment terms 14 days, creators need approval, close rule `none`, manual payments not counted as verified revenue, owner-only refund records, write-offs, settings and payment account. A manual payment needs a method and at least three characters of evidence; a card number or key typed into free text is refused; an invoice with a payment cannot be voided (a test invoice can, D45); a write-off is final and never revenue (a late payment can still be recorded). A privacy request deletes unissued invoices and blanks only the frozen bill-to of issued ones, keeping number, amounts, dates and payments. The number is a label, not a compliance claim (no country's tax-invoice rule is promised). Agency staff hold no `invoices.*` permission and no support-session read. **Status:** engineering; **founder, counsel and the accountant confirm** the defaults, what an erasure request does to issued invoices and their free text, the retention period, and numbering and tax wording by jurisdiction; whether any agency read of invoices is wanted.

## D42. Customer payments: the client's own account, sealed keys, every real call gated

The client collects through its own PayMongo (PHP only) or PayPal account; iAcquire never holds funds, never charges a customer and never sees a card, and no fee for iAcquire is coded. Only the owner connects the account (`invoices.connect_payments`) after accepting recorded wording (draft wording, not counsel-approved; the accepted version, who and when are stored). The keys are sealed (AES-GCM) in a column the application role cannot read, behind one seam (`credentialVault` in `src/server/customer-payments/credentials.ts`); moving to Supabase Vault (what the audit and migration 0010's rule recommend) would change that file and the column and nothing else. **Every call to a real provider, reads included, needs `CUSTOMER_PAYMENTS_WRITES_ENABLED`** (stricter than the audit, to honour the hard rule literally), and real money needs `CUSTOMER_PAYMENTS_LIVE_ENABLED`, the owner's recorded authorization, a provider-confirmed test payment and the owner's confirmation. A customer is never sent to a provider's test mode. The provider's return address carries our checkout reference, never the invoice link. Webhook deliveries that are not ours are acknowledged and not stored; a delivery that arrives is recorded whatever the switches say (PayPal excepted, D23). Provider keys are checked, never echoed. **Status:** engineering; **founder decides the credential store** (sealed column or Vault) and the key rotation procedure (`decryptSecret` ignores `APP_ENCRYPTION_KEY_PREVIOUS`, so a rotation makes every sealed credential unreadable), the entitlement and any fee, counsel approves the wording, and a sandbox run settles the guesses listed in the adapters' headers.

## D43. Nothing is paid, signed or accepted on a guess

Only a verified provider fact or an explicit, audited human record changes money. `src/server/invoices/apply.ts` is the only writer of paid, refunded and payment status and of payment and refund rows (a source-scan test fails otherwise) and the database refuses an invoice whose amounts and status are not what its rows add up to. A payment counts only when the connection's mode, the reference, the provider's checkout id, the amount, the currency and (where asked) the provider's read-back all agree; anything else is kept as a row for a person and counts for nothing. A webhook is trusted only by its signature, checked with that connection's own secret; its receipt is committed first, then applied, then marked on error (three transactions), so a failure leaves a receipt a later delivery or the reconcile job applies again; the raw body is never kept. The customer's page says "We are confirming your payment" until the database counts it. **Status:** engineering; no confirmation needed.

## D44. What verified revenue means

A payment is verified revenue when the provider confirmed it, it was live money, it was received (succeeded, or partly or fully refunded since) and is not held out by a dispute still open, and it was received on or before the report's as-of moment. Revenue is the payment less the tax in it, less what was refunded and the tax in the refund, per currency, never added across currencies, as a cohort to date. Test mode, the simulated provider and a test invoice never count; a payment recorded by hand counts only if the owner opted in (`count_manual_as_verified`) and the report says so; deal value is never called revenue and no return figure comes from deal value. It is shown only to people with `invoices.view` and only where invoicing is on. **Deviation from the audit:** the connection is not required to be *still* live-confirmed when the report is made, because replacing keys or disconnecting clears the confirmation and revenue would vanish on a rotation or at offboarding; a live provider-confirmed payment can only exist because a checkout started while the connection was confirmed. A one-line change makes it stricter. The rules exist twice (TypeScript and SQL) and a test runs both over the same random payments. **Status:** engineering; founder confirms the live-confirmation reading and whether hand-recorded money may ever count.

## D45. Test invoices: who marks them, how they are numbered, what deleting one costs (extends D22)

Marking, unmarking and deleting a test invoice is the owner's alone (`invoices.connect_payments`, as "Pay as a test"): otherwise a salesperson could hide a real invoice from receivables by marking it a test. The mark is chosen on a draft and fixed once the invoice leaves draft; a test invoice takes `TEST-0001`, `TEST-0002` from its own counter (`customer_invoice_settings.next_test_number`) so the business's real sequence has no gap; it is offered only while a test-mode payment account exists, is labelled everywhere including the printed page, is never reminded about (the database drops a reminder row for one), is out of owed, overdue, verified revenue, deal rules, automations and the receivables review, accepts no hand-recorded payment, refund or dispute, and can be voided or deleted with its test payments. The simulated provider is always test mode, so in development it can take a test invoice only (a real invoice shows "pay another way"). **Cost:** deleting the only test invoice removes the provider-confirmed test payment that lets an owner go live; the dialog warns and offers void. **Status:** engineering; the owner-only reading and the `TEST-` counter are proposals (change `mustMarkTest` and the form's `canMarkTest` if managers should mark them).

## D46. Invoice reminders go through the consent chain and need the owner's exact words

Reminders are service messages under a new `billing` scope through `evaluateSend` and `queueOutbound`: consent, opt-outs, quiet hours, a person's hold, credits and the provider write switches all apply; a reminder is registered after the dispatcher so it leaves on the next tick. The wording is fixed in code (no AI, nothing a customer typed), version `draft-2026-10-23`, carries `{{invoice.link}}` as a placeholder and the invoice total (never a balance, because a queued message can wait while a part payment arrives); the link is derived only for the provider call. The owner authorizes the exact wording, days, channels and maximum (a fingerprint); it lapses after 90 days, on any change, a new wording version, or the authorizer leaving the owner role. Defaults offered: 3 days before, on the day, 3 and 10 days after, at 09:00 workspace time, at most four, **email only** (text and WhatsApp use prepaid service credits, so they are the owner's choice, and the channel list is part of what the owner authorizes). A payment, void, write-off or dispute withdraws unsent reminders; a held reminder is sent up to 24 hours late and never later; a test-mode payment starts no workflow. **Status:** engineering; **counsel or the founder approves the wording** (and any late-fee text); the 90 days, 24 hours, 09:00 and the default days are proposals.

## D47. Reputation: the review-gating-safe rules are law, enforced by code and by a static test

R1 one page and one set of links for every rating; R2 who is asked never depends on how they feel (ask selection may use only a completed-service fact, channel and address, service consent exactly `granted`, suppression, the 30-day cool-down, quiet and business hours, credits, and a person's explicit per-contact hold); R3 a low score adds a private follow-up and never replaces anything (the thank-you page differs by one sentence); R4 no incentives and no asking for a particular rating (a blunt word list that **blocks**, not warns); R5 never fabricate (no method exists to write, hide or delete a public review; simulated rows carry a "Simulated" badge and never exist in production); R6 replies are drafted by AI at most, approved by a person for one version, posted by a person with `reviews.reply_publish`, and the posted text must equal the approved text; R7 customer messages only through `evaluateSend`, with a private link needing consent `granted` on the channel used; R8 a person-set hold is audited with a reason and counted. A low score opens a task for the owner, a notice naming the customer and score (never their words, because notices can be emailed), an urgent complaint escalation in the inbox, stops the customer's remaining program messages and emits `feedback.escalated`; a workflow that event starts may not contain a review request. One 30-day cool-down is shared by every kind and source. `tests/reputation-gating-guard.test.ts` reads the source of ask-selection, link-selection and every batch file and fails on feeling words or an unlisted table. **Status:** engineering; **counsel confirms** the word lists, the thank-you sentence, the single shared cool-down, and that stopping a customer's remaining program messages after low feedback is acceptable.

## D48. Surveys and batches are separate dormant modules with hard limits

Surveys (`reputation_surveys`): a request has a kind (review or survey) and a scale (CSAT 1 to 5, NPS 0 to 10) decided by the request, never by the form; a score is shown only from a sample size (at least 10 answers on the five-point scale, at least 30 on the zero-to-ten scale; below it the screen says how many answers there are and how many are needed); NPS uses the standard groups whatever follow-up level the workspace chose; anonymous survey answers and hand-recorded feedback are reported apart and never scored. Batches (`reputation_batches`): criteria are a strict object of six keys (`source`, `from`, `to`, `calendarIds`, `appointmentTypeIds`, `pipelineId`) repeated as a database CHECK, so no feeling-shaped key can be stored; only customers with a completed service in a past window of up to 366 days, one row per customer; up to 1,000 people; the preview is one set-based query kept in step with the per-person check by a parity test; **only the owner approves** (`campaigns.send`), the approval is bound to a hash of the template version, criteria, channel, kind, scale, pace and the business details the wording uses, and lapses after 14 days; a manager can only ask the owner; pace 1 to 60 a minute (default 10) spent inside the batch's row lock; at most 20 unfinished batches per workspace; credits, budget, channel or a missing public link **pause** a batch, any drift in what the owner approved **stops** it for good (statuses `paused` and `stopped` were added to the audit's list because a bulk send needs a pause and a system stop must be told apart from a person's cancel). **Status:** engineering; **all numbers are proposals**; founder decides whether managers may approve a batch and where each module sits commercially; the batch job is the first reputation job that writes to customers, so it belongs to a later staged-start step.

## D49. Public reviews are read-only, replies are a person's, Facebook replies are off until proven

Reviews are copied once, keyed by the site's own id; a review the site stops returning is marked removed only after a complete pass that read at least as many as the site reports (and restored if it returns); the first read of a connection announces only reviews under 48 hours old; entries with neither a star rating nor a recommendation are not stored; a reviewer is never matched to a customer by name (a person may link one by hand). A reply is approved by version (a hash of the workspace, connection, review, the site's review id, a fingerprint of the review as read, the version and the exact words), only the owner or an admin approves and posts (an owner may approve their own), the intent is written before the request leaves, and a lost answer becomes "result being checked" and is never sent again on a guess (found on the site: posted; absent for 10 minutes: failed with a retry offered; no answer after 24 hours: the owner and managers are told to look). A Facebook connection is created unable to post replies (a person posts on Facebook and says so); `can_reply` follows the permissions the Page was granted. The AI reply assist is off unless the workspace turns it on, labelled "AI-drafted", rate limited (20 an hour per person, 50 a day per workspace), metered (`review_reply_ai`), and never submits, approves or posts. Retention proposals: a disconnected site's reviews 90 days, reviews the site stopped returning 90 days, finished reply history 730 days. **Status:** engineering; **retention periods and the reply rules are proposals for counsel**; whether Meta allows replying to recommendations at all is unknown.

## D50. AI cost: record every call, charge only where a rate is published, cap the public chat

`src/server/llm/meter.ts` records one usage line per token unit in `metered_usage_events` (tagged `ai:<feature>`), charges credits per 1,000 tokens only when an `llm` unit rate is published (none is, so every line is zero cost and no price is invented), is idempotent per call key, never throws (on failure it logs the error class and opens one platform incident per feature), and records a failed call that still carried usage. The public website chat has a per-workspace daily allowance of AI replies taken before the model is asked (default 500, `WEBCHAT_DAILY_AI_REPLIES`, a fixed UTC-day counter in `rate_limit_buckets`; past it the visitor is told a team member will follow up, a person is asked, and the owner gets one notice a day), and a global kill switch `WEBCHAT_PUBLIC_DISABLED`. **No migration was allocated to chain D,** so the audit's new `usage_events` kinds and `usage_limits` columns were not built; the cap therefore cannot be set per workspace and the zero-cost lines are not shown on the client's usage page. `usage_limits` is not applied to channel replies. Social AI no longer counts against the monthly help allowance (its per-user and per-workspace limits and the credit balance remain). **Status:** engineering; founder confirms 500 a day, publishes the `llm` rates (units `ai_tokens_in` and `ai_tokens_out`, per 1,000 tokens), decides on a per-workspace override (a hardening migration in the 0099 to 0103 range) and who is paged when the metering incident opens.

## D51. A typed address is unreachable by anything automatic until it is confirmed (extends D25)

`evaluateSend` refuses `identity_unverified` for a contact the website chat created when the address is unverified and typed by the visitor, for anything automated or promotional (workflows, campaigns, reminders, retention, follow-ups, system sends, unapproved AI replies); a person's one-to-one message and an AI draft a person approved still go; a scope added later fails closed. The consent ticked in the chat form is recorded with its exact wording and the evidence "Typed by the visitor in the website chat, unverified", and a promotional tick whose latest source is the chat form never counts, even after the address is confirmed, until consent is recorded again by a person. An address becomes verified when a message arrives from it with the sender proven (SMS or WhatsApp through the carrier; email only when the receiving server authenticated it), or when a person with `contacts.edit` confirms it in the Inbox with a written reason of 5 to 300 characters (audited, without the address). No email-link or SMS-code verification flow was built. **Status:** engineering; founder decides whether reminders and retention messages for a visitor who booked or bought should stay blocked until confirmed (today they do), who may confirm (`contacts.edit`, or owners and admins only), and whether a real verification flow is wanted.

## D52. AI checks are heuristics, tested against stubs, and they fail toward a person

The proposal claim and number rules (D40), the web chat reply check, and the reply rules (D49) are pattern lists in English, written from the reviewers' examples and our variants and tested only against stub model output. A proposal sentence that fails is dropped; a web chat reply that fails takes the existing honest "unavailable, a team member will follow up" path (an internal note, one escalation); a reply draft that breaks a rule is not saved. They can over-refuse (a person then replies) and can miss amounts spelled in words in the web chat. They are a net, not a guarantee: a person reads and approves every proposal draft and every reply. **Status:** engineering; **no real model has been evaluated**, which the founder should treat as a gate before any of the three features is switched on for a real client.

## D53. A stopped workspace's public pages go quiet, but money in flight is still recorded

A suspended, archived or iAcquire-paused workspace's proposal page, invoice link, pay and status paths, signing webhook, emailed codes and expiry job refuse or skip it (the link shows "unavailable"; no "opened" is recorded), via a shared reading of "this workspace takes no customers". Deliberately not gated: payment webhooks, read-back, the return page, the status-by-reference check and the PayPal capture (money already on its way is recorded), and the team's own screens. Offboarding shutdown sets the pause and disconnects the signing account, the payment account and the review sites. **Status:** engineering; founder confirms that a shut-down client's customer links should say "unavailable" rather than keep showing proposals read-only until deletion.

## D54. Privacy requests: withdraw and blank, keep the record, say what was kept

A privacy request withdraws a person's unfinished proposals, closes their links, ends open signing requests, deletes emailed codes and sessions, blanks name, company and address on working copies and links, resets a proposal title that contains the person's, their company's or the proposed-to name and blanks the notices that named it, deletes unissued invoices and blanks the frozen bill-to of issued ones, removes feedback comments and form-survey answers (keeping the score so counts survive), cancels unanswered review requests, and follows contact merges (it runs for the kept contact and every contact merged into it). It **keeps** frozen proposal versions, recorded answers, signing requests, history and signed copies, issued invoices' numbers, amounts, dates and payments, and the audit trail, and returns a count of what it kept; typed notes, sections and terms are left for the business to review and counted. Append-only tables (events, decisions, invoice events) can be deleted only under `iaq.purge` during a workspace's final deletion, which removes everything including accepted proposals. **Status:** engineering; **counsel and the founder decide** whether an accepted proposal or a signed record may be erased on request, for how long invoices, receipts and signed copies are kept, and whether keeping a score is acceptable in a given jurisdiction.

## D55. Unreleased migrations are edited in place, and the rehearsal is rerun each time

Migrations 0087 to 0095 have never been applied to any hosted database, so the build and the fix wave amended them in place (0087 `typed_by_visitor`; 0090 the support-session rule for proposal documents; 0091 purge deletes and indexes; 0093 `reminder_channels`, `is_test`, `next_test_number`, the issue and insert guards; 0094 batches, `form_submission_id`, `renewal_reminders_enabled`; 0095 `possible_contact_id`), each with its rollback, its entries in `scripts/rehearse-combined-migrations.mjs` and `tests/crm-migrations.test.ts`, and a rerun of the combined rehearsal. Why: one clean set is easier to apply than a chain of corrections on top of a set nobody has run. Consequence: a local QA database that applied an older version lacks the later columns and triggers and must be rebuilt by re-running the seeds; and the first hosted dry run must use these files as they are now. Once any of them is applied anywhere, it is frozen and a change becomes a new migration. **Status:** engineering.

## D56. A test may not open a connection to another machine

A vitest setup file (`tests/support/no-network.ts`, commit `b47380f`, with its own test `tests/no-network-guard.test.ts`) refuses every socket that is not loopback (a name with its own lookup is judged by the address the lookup answers) and fails the test that tried even when the code catches the error. Why: stage B2 sent about five unauthenticated requests to the real `api.paymongo.com` from a test whose stub had been removed (all answered 401; see the checkpoint, section 9). The hard rule was "no real provider call", and nothing enforced it. **Status:** engineering; no confirmation needed.

## D57. Browser-side contracts are guarded by tests, because Node tests cannot see them

Four defects passed every Node test and were found only by building the app or driving it in a browser: a server page called a function exported from a `"use client"` file; a same-origin native form post from a page served with `Referrer-Policy: no-referrer` arrives with `Origin: null` and was refused; `node:crypto` reached the browser bundle; and the simulated payment provider reused payment ids after a restart. The guards: `tests/client-bundle-safety.test.ts` walks every server page and every client component and fails on a function or constant imported from a client module into server code and on a `node:*` or server-only import reachable from client code; `src/server/security/same-site.ts` is the one same-site check (it falls back to `Sec-Fetch-Site` when `Origin` is `null`; `tests/same-site.test.ts`, `tests/same-site-audit.test.ts`); simulated payment ids are unique per process. The rule for later work: a change that touches a `"use client"` file, a page or a public form needs a test of the browser-side contract, or a plain statement that it was not checked in a browser. **Status:** engineering; no confirmation needed. Not yet verified: that a `fetch()` POST from a no-referrer page carries a real `Origin` in Chrome, Safari and Firefox (the older public booking endpoints rely on the Fetch standard for it).

## D58. Purchase intents use a verified manual payment until a provider is approved

A purchase intent freezes US$1,499 setup and the optional US$299/month plan in its own row, keeps only a SHA-256 hash of a random 32-byte link, and records the buyer's confirmation. A Super Admin then records the payment they checked (amount, method, external reference, day, note) and only after that can the existing `createClientTenant` and `recordManualPayment` services make the workspace. Why: no PayMongo/PayPal account, signed webhook or recurring-billing mechanism is available or approved, and a workspace must never be created from an unverified event. The public page takes no card, creates no user and cannot choose an amount. **Status:** engineering; the online checkout and provider-webhook auto-provisioning remain **Not built**, and the $299 plan is a recorded choice, not an automatic subscription. Founder approval is needed before live collection.
