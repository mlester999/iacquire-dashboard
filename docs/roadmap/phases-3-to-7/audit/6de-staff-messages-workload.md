# Phase 6D/6E: internal staff Messages and staff workload management (agency side)

## Summary
Neither feature exists anywhere in the repository. A search of all 65 refs for staff-messaging and workload tables and code found only false positives, and no ref has a migration that HEAD lacks except 0084 (the Hermes provisioner). What does exist is solid raw material. There is a tested agency role and permission framework (agency_staff, agency_manager and agency_super_admin, with per-person overrides and client scope via app.user_can_access_org). Per-module assignment and escalation exist in Support, Projects, Setup and Maintenance. There is a hardened notifications table and a scheduler registry. The Setup Center is a working SSE, Supabase Realtime (topic setup:<org>, revision only) and polling precedent, though hosted Realtime is documented as unverified. The workload data is thin and uneven. Only support_tickets, client_setup_tasks, client_project_requests, maintenance_requests and project_review_tasks carry an assignee. project_review_tasks.assigned_to is never written, maintenance has no assign function, support overdue is computed only if SLA targets are enabled (default off), and no agency capacity, skills or time-off data exists. The recommended build is two additive migrations: 0090 for staff messages, then 0091 for workload. Both are agency-only, keyed on users.platform_role and not on org membership, and gated by new agency.messages.* and agency.workload.* permissions that no client role has. Messages need a new 'staff' notification audience, because the existing 'direct' audience leaks to a demoted agency user. Workload is a pure rules engine over live rows from existing tables, with no new task table, no AI and no invented availability.

## Risks
- Notification audience change touches shared code used by every module (feed, unread count, mark-read, notification_visible, email job). Regressions would be cross-cutting; extend tests/notification-authorization.test.ts and keep the change additive.
- Shared secrets in plain view: staff messages are protected by RLS and server checks, not encryption. Anyone with the system DB role, backups or the service role can read them. Say so; do not claim private-by-cryptography.
- app.file_permission has been re-created seven times (0011, 0015, 0020, 0039, 0044, 0049, 0089); copying any older body silently drops buckets. Start from the 0089 body, add one branch, and extend the existing regression test. A permissive read for 'staff-messages' would let any agency user download any attachment through Storage.
- The agency override CHECK lists in agency_user_permission_overrides and invitation_agency_permission_overrides were last rewritten from a copied list in 0065. Adding delegable permissions means rewriting them again: use the read-back DO-block approach and declare MIGRATION_PREREQUISITES (0065, 0067, 0089).
- Hosted Supabase Realtime is unverified, so the baseline is SSE plus polling (5-20 s latency). Do not present sub-second delivery or typing indicators as working until tested on a live project.
- Serverless realism: streams last at most 60 s and reconnect; with DATABASE_POOL_MAX defaulting to 4, each stream tick must stay a single indexed primary-key read, and per-user stream caps must apply.
- Employee-monitoring sensitivity: labelling named people Overloaded or Critical is HR and privacy-sensitive. Keep it to the person and managers, never to clients or peers, show the rule that fired, and get the founder's decision before showing peer visibility.
- Workload only reflects work recorded in the portal. Internal agency tasks, meetings, AI-employee work, client CRM tasks and Unified Inbox conversations are excluded by design (client-owned or not recorded). The page must state this, and no label should be shown as a performance score.
- Data gaps that can mislead: support overdue is 0 whenever SLA targets are off; maintenance has no due date; project_review_tasks.assigned_to is dead; claim-on-first-touch (assigned_to = coalesce(assigned_to, actor)) shifts load silently. Surface 'unknown' states instead of defaulting to healthy.
- Cross-client leakage inside agency tooling: workload item details and message context references must respect each viewer's client scope (app.user_can_access_org). A manager scoped to assigned clients, or a staff member, must get aggregates only for work on clients outside their scope. Never copy ticket subjects or client names into message bodies automatically.
- A staff member demoted to platform_role 'none' (or later invited as a client user) must immediately lose messages, attachments and notification history. 'direct' notifications and any membership-only check would not guarantee this.
- The agency organization may not exist in fresh or test databases. org_id on the new tables must come from the single kind='agency' organization (unique index organizations_single_agency); services fail closed with a clear error. Tests must create it via createOrg({kind:'agency'}).
- Offboarding and export enumerate tables with an org_id column (src/server/offboarding/service.ts:289-296, export.ts:149). Using the agency org id keeps client deletion from touching staff data; never add a client org_id column or cascading FK to client rows on staff tables (use soft reference columns with different names).
- Migration numbering and rollout: next free number must be re-checked immediately before creating 0090/0091 (0084 reserved on other branches, 0073-0076 gaps). Nothing may be applied to the hosted database without founder approval; the jobs stay dormant until the scheduler stage that includes them is approved.
- Ranking and suggestions must stay deterministic and explainable (rules, not AI). An AI-written staffing suggestion would breach 'no seventh AI Employee' and 'never fabricate'; keep the Performance Analyst out of this.
- Hot-conversation contention: per-conversation seq is assigned by an UPDATE on the conversation row (serialises writers). Fine at agency scale; cap members per channel (for example 200) and message body size.

## Findings in existing code
- [medium] src/server/support/agency.ts:432 assignRequest sets support_tickets.agency_last_read_at = now() as a side effect (same pattern at lines 270, 313, 365, 390). That marker is one timestamp for the whole agency, and client_waiting/'client_replied' are computed as 'client message newer than agency_last_read_at'. A manager who reassigns a request without reading it therefore clears the 'client replied' flag for the new assignee while the client's message is still unanswered. Any workload signal for 'client waiting' built on it would be wrong.
- [medium] src/server/notifications.ts:110 notifyUser gives agency users with no org the audience 'direct'. app.notification_visible (0067) returns true for 'direct' unconditionally and the client feed also lists audience 'direct' (lines 220, 243, 288, 295). If an agency account is later demoted to platform_role 'none' or the same person is invited into a client workspace, their earlier 'direct' notifications (titles and bodies) appear in their client feed. This is minor today but becomes a real leak once staff-message notifications exist; it is why a separate 'staff' audience is recommended.
- [low] src/server/projects/client.ts:204 project_review_tasks are inserted here and at lines 238, 383 and 387 without assigned_to, and nothing in src writes the column (0015_custom_projects.sql:272). ## Founder decisions
- Scope of 'staff': recommended agency roles only (Agency Staff, Manager, Super Admin). Confirm that client-organisation teams get no internal chat from this work (a per-tenant feature would be a separate decision).
- Can the Super Admin read other people's DMs or private groups (compliance, investigations)? Recommended default: no; they can moderate channels only. If yes, it needs an audited, reasoned break-glass action and a notice to staff.
- Retention and departure handling for staff messages (keep forever, a fixed period, export on departure) and any employee-monitoring notice or consent wording; needs legal review before real staff use.
- Workload policy numbers: item point weights, default capacity points, label thresholds, floors, the 5-working-day horizon, and project-health thresholds. The engine is rules-based, so these are policy, not facts: the founder must approve before labels are shown.
- Who sees labels: recommended each person sees their own, managers see everyone's, never clients and never peers. Also whether staff can edit their own time off and skills (recommended: time off yes, skills managers only).
- Whether work that isn't recorded in the portal (internal agency tasks, meetings) needs a place to be recorded; recommended not now, with a visible 'counts only work recorded in iAcquire' note.
- Whether to approve verifying hosted Supabase Realtime for staff messages (needs a live-project test) or stay on SSE and polling; and whether typing indicators are wanted at all.

## Recommended design
## 0. Principles
* Messages and workload are agency-only. Access is derived from users.platform_role (active) plus a permission, never from organization membership or client roles. No new object has a client audience, no Automation Studio trigger, and nothing enters AQi/Hermes context.
* Reads go through withUser under RLS (second boundary); writes go through withSystem inside one transaction after the service has re-read role/permission/membership from the DB (the social/support pattern). SELECT-only grants to iaq_app_user; nothing to anon/authenticated.
* Workload is a computed view of existing tables. No generic task table, no fabricated availability or progress, no AI. Every label shows the rule that produced it.
* Two migrations so each can be rehearsed, rolled back and approved on its own: 0090_staff_messages, 0091_staff_workload (re-check numbers with scripts/rehearse-phase3-migrations.mjs section A first). Each gets supabase/rollbacks/*.down.sql, a migration test, and a MIGRATION_PREREQUISITES entry (0065, 0067, 0089; 0091 also 0090).

## 1. Permissions (src/lib/permissions.ts + role_permissions rows + AGENCY_PERMISSION_INFO)
Messages: agency.messages.use (agency_staff, agency_manager, agency_super_admin; delegable so a person can be denied), agency.messages.channels (manager, super; create channels/groups of any kind, manage channel members; delegable), agency.messages.moderate (super only, non-delegable: archive any channel, delete messages in channels; NO read access to DMs or private groups the person is not in).
Workload: agency.workload.view (all agency roles: own load, own items, own time off), agency.workload.team (manager, super; everyone's labels, board, calendar, analytics; delegable), agency.workload.assign (manager, super; delegable; the board action ALSO needs the module's own assign permission: agency.support.assign unless self-claim, projects.manage, setup.manage, maintenance.manage), agency.workload.manage (manager, super; capacity, skills, time off for others; delegable), agency.workload.settings (super only; weights, thresholds, default capacity).
No client role appears in any of these rows. Extend the two agency-override CHECK lists using the read-back DO-block pattern, add the delegable ones to AGENCY_DELEGABLE_PERMISSIONS, and the rest to AGENCY_TEAM_PROTECTED_PERMISSION_INFO. tests/workforce-config.test.ts will fail until PERMISSION_MATRIX and the DB agree.
Helpers (SECURITY DEFINER, search_path pinned, statement-level so the 0060 InitPlan guard stays happy): app.staff_messages_allowed() = app.is_agency_staff() and user_has_agency_permission(me,'agency.messages.use'); app.staff_conversation_ids() uuid[] = active memberships of the caller when allowed(); app.can_view_staff_workload(p_user) = self, or workload.team holder.

## 2. Migration 0090 (messages). Every table has org_id = the single agency org (guard trigger rejects kind<>'agency'), unique(id, org_id), composite FKs, RLS on
* staff_conversations(id, org_id, kind 'direct'|'group'|'channel', name (null for direct, 1..80 otherwise), topic, visibility 'staff'|'private' (channels), direct_key text unique (sorted user-id pair, one DM per pair), created_by, archived_at, last_seq bigint, last_message_at, created_at).
* staff_conversation_members(conversation_id, user_id, org_id, role 'owner'|'member', joined_at, left_at, muted, notify 'all'|'mentions'|'none', last_read_seq bigint, last_read_at, PK(conversation_id,user_id)). Active = left_at is null. Cap members per conversation in code.
* staff_messages(id, org_id, conversation_id, seq bigint, thread_root_id (same-conversation composite FK, one level), author_id, body 1..8000, mentions uuid[], client_message_id uuid, edited_at, deleted_at, deleted_by, created_at; unique(conversation_id, seq); unique(conversation_id, author_id, client_message_id) for idempotent send; trigram GIN on body behind the optional-extension guard). seq is assigned by update staff_conversations set last_seq=last_seq+1 ... returning in the same transaction.
* staff_message_reactions(message_id, user_id, emoji from an allowlist, org_id, PK all three).
* staff_message_attachments(id, org_id, conversation_id, message_id null until sent, private_file_id with FK (private_file_id, org_id), uploaded_by, status 'staged'|'attached'|'removed', expires_at, filename/mime/size). Bucket 'staff-messages' added to private_files_bucket_check; PrivateBucket + MIMES (pdf, png, jpeg, webp, txt, csv, docx; 10 MB; 5 per message; signature check). file_permission: write = agency staff with messages.use on the agency org; READ = false for browsers; downloads only via /api/admin/messages/files/[id] after a membership check, then readAuthorizedPrivateFile.
* staff_conversation_events(append-only, immutable trigger; kind created|member_added|member_removed|renamed|archived|unarchived; ids and enums only).
* staff_inbox_state(user_id PK, org_id, revision bigint): bumped in the sending transaction for each affected active member. It is the only thing streams and polls read.
* Notifications: audience CHECK gains 'staff'; app.notification_visible: staff -> active user with platform_role<>'none'. Update the three feed predicates in src/server/notifications.ts (agency branch includes 'staff'; the client branch already excludes it). New helper notifyStaff(db, userId, kind, ...) writes audience 'staff', org_id null, content-free body ('New message from X'), dedupeKey 'staffmsg:<conversation>:<member.last_read_seq>' so one unread burst gives one notification. New kinds via the read-back DO block: staff_message_direct, staff_message_mention, staff_message_added, staff_workload_alert, staff_work_overdue. Register them in IN_APP_BY_DEFAULT and CUSTOMER_CONTENT_KINDS (title and link only, never emailed with body).
* Realtime policy iaq_staffmsg_realtime_read on realtime.messages: extension='broadcast' and realtime.topic() = 'staffmsg:'||app.current_user_id() and app.staff_messages_allowed().
State machines: conversation active -> archived -> active (owner/manager/moderate); membership active <-> left (also set by the maintenance job when the user is disabled or no longer agency; messages keep the author and render 'Former team member'); message posted -> edited -> deleted (tombstone, body cleared); attachment staged -> attached | removed (TTL cleanup).

## 3. Services (src/lib/staff-messages/*, src/server/staff-messages/*)
Pure rules: direct_key, body normalisation, mention parsing (mentions validated against members), emoji allowlist, unread math, thread rules. Server: conversations.ts (createDirect idempotent via direct_key, createGroup, createChannel, join/leave/addMembers with eligibility = active agency user holding messages.use), messages.ts (send with clientMessageId idempotency, thread reply, edit own, delete own, moderate delete, react), read.ts (monotonic greatest() cursor), search.ts (scoped to staff_conversation_ids()), attachments.ts (stage -> bind -> TTL cleanup), directory.ts (people picker via a SECURITY DEFINER staff directory, because users RLS hides other staff), notify.ts, access.ts (assertStaffMessagesAccess re-reads status, role, permission, membership each request). Rate limits: new RATE_LIMITS (send, create, search, upload). Audit: conversation/member events only, never bodies. Optional phase 2: soft context links (ref_kind, ref_id, ref_org_id, no FKs) resolved live per viewer with user_can_access_org, rendered as 'something you don't have access to' otherwise.
Realtime: (1) baseline: visible-tab poll of a snapshot endpoint with ?since=<revision> every 15-20 s and on focus; (2) SSE GET /api/admin/messages/stream cloned from setupEventStream: revision-only frames, 5 s poll of staff_inbox_state, 60 s max, 4 streams/user, access re-check each tick emitting access_changed; (3) optional Supabase private topic staffmsg:<userId> with a token route modelled on setupRealtimeToken and publish-after-commit modelled on publishSetupRevision, enabled only after a live-project test. Typing indicators deferred. Read AGENTS.md: check node_modules/next/dist/docs before writing the route handlers.

## 4. Migration 0091 (workload). Same org_id/RLS conventions
* staff_work_profiles(user_id PK, capacity_points int null 1..200, working_days smallint[] default {1..5}, skills jsonb {skill: 1..3} validated against a code list (support, setup, crm, website, ai_employees, integrations, billing, projects, maintenance), updated_by).
* staff_time_off(id, user_id, starts_on, ends_on, part_day bool, kind leave|sick|holiday|training|other, note<=200, created_by). Staff may edit their own; managers anyone's (workload.manage).
* staff_workload_settings(id boolean PK, rules jsonb (weights, thresholds, horizon_days, default_capacity_points), revision). Defaults live in code; the row only stores super-admin overrides.
* staff_workload_snapshots(identity id, user_id, taken_at, label, points, capacity, overdue, items, capacity_source, rules_revision; immutable; written only when label or points change plus one per local day; 400-day retention). Counts only, no client names.
* staff_workload_alerts(id, user_id, label 'overloaded'|'critical', since, notified_at, resolved_at; one open per user) for escalation duration and idempotent notifications.
* work_assignment_events(id, source, item_id, from_user, to_user, actor, via 'board'|'suggestion', created_at) for board-originated reassignments (modules keep their own events).

## 5. Workload engine (src/lib/staff-workload/{sources,rules,labels,suggest,health,calendar}.ts; pure, injected now)
Work-item projection (server SQL UNION, computed on demand, scoped by app.user_can_access_org for the viewer): support_tickets (active statuses new/open/in_progress/waiting_for_client; due = support_ticket_ops.response_due_at, escalated = escalated_at), client_setup_tasks (assigned, not completed/hidden/service_excluded, instance not activated, org not archived/suspended; due = estimated_completion_at; blocked/waiting flags), client_project_requests (active statuses; due = earliest open review-task due_at or client_projects.expected_completion_on), project_review_tasks (open; assignee = request assignee because assigned_to is dead; counted for due/overdue only, not points), project_milestones (calendar and health only), maintenance_requests (open/in_progress/waiting_for_client; no due date). An Unassigned lane lists the same sources with assignee null. Excluded by design: Unified Inbox conversations, CRM tasks, AI work jobs.
Points (explicit, editable by workload.settings, shown on a Rules panel; proposed defaults for founder approval): support urgent 5, high 3, normal 2, low 1, waiting_for_client x0.25, escalated +2; setup task 2 (optional 1), blocked x0.5, waiting x0.25; project request by status (submitted/under_review/discovery 2, quote_preparing 3, quote_sent/awaiting_approval 1, approved 2, in_development 5, testing 3, ready_for_review 2, on_hold 0.5); maintenance 2, waiting x0.25.
Capacity over a horizon of 5 working days: capacity_points (person, else agency default, flagged capacity_source) x available fraction (working_days minus staff_time_off; part day = 0.5). Ratio = points/capacity (capacity 0 with points > 0 is Critical with the reason 'away for the whole horizon').
Labels: <0.50 Available, <0.85 Balanced, <1.00 Busy, <1.25 Overloaded, >=1.25 Critical. Floors from real data: any overdue item -> at least Busy; an escalated item or 3+ overdue -> at least Overloaded; 5+ overdue -> Critical. If capacity can't be determined (no default configured) the label is null and the UI says 'capacity not set'. Output always includes points, capacity, ratio, reasons[], and data-quality flags (items with no due date, SLA targets off, capacity from default).
Suggestions: candidates must be active, in scope for the item's client, hold the module permission, and have capacity > 0 over the horizon. Rank by skill fit (only if skills recorded), then label rank, then projected ratio after assignment, then continuity on the same client, then least recently assigned; return top 3 with reason strings. Applying one calls the existing module function (assignRequest, assignProject, updateTaskDetails; a new small assignMaintenanceRequest replaces the silent claim) and writes work_assignment_events plus audit.
Project health: on_track | at_risk | off_track | not_enough_data from overdue milestones, blocked milestones, overdue review tasks, expected_completion_on passed, and days since last_activity_at (threshold in settings); progress = completed/total milestones only when milestones exist. Waiting-on-client is shown as such, not blamed on the team.
Escalation tracking: union of support escalations, overdue beyond the support escalation threshold, unacknowledged critical incidents, and open staff_workload_alerts with duration.
Jobs (tick.ts, JOB_LABELS, and both registration tests): staffWorkloadSnapshots (everyMinutes 15; computes, writes snapshots, opens and resolves alerts, notifies managers once per user/label/day via staff_workload_alert, notifies assignees of overdue items once per day via staff_work_overdue), staffMessagesMaintenance (everyMinutes 60: expire staged files, close memberships of ex-staff, apply retention only if a retention period is configured).
