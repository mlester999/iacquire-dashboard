# Phase 5F/5G: reputation management (reviews, surveys, escalation, reply drafts) and customer retention

## Summary
The ledger calls reviews 'partial' but the private half of reputation is a working, tested slice that is byte-identical on master, origin/master, feat/phase2-lead-conversion, integrate/unified-inbox-workforce and worktree-aqi-operations: public review destinations, consent-gated review requests with hashed bearer tokens, the /r/<token> page that shows the same public links to everyone, private 1-5 feedback with a task plus notification for ratings of 2 or less, a funnel report, a request_review workflow step and an appointment.showed Studio template (src/server/crm/reviews.ts 1,054 lines, tests/crm-reviews.test.ts 621 lines; I read the tests but did not run them). A second, separate system exists for retention: five owner-approved, hash-bound message programs (migration 0024, src/server/retention/*, tests/retention.test.ts 458 lines) sent under the CRM Manager identity through the same evaluateSend chain, but its feedback_request program is free text with no link, so replies are unstructured and never reach customer_feedback. Nothing exists anywhere for Google Business Profile or Facebook review sync, replying, external-review storage, AI reply drafting, NPS/CSAT, per-customer surveys, bulk review asks, renewal reminders or any reputation capability for an AI employee; I searched about 65 refs and about 40 sibling worktrees by content and file name and found no stray implementation to port, and no ref uses a migration number above 0089. I also found real defects on the path: contact erasure ignores private feedback text, contact merge leaves feedback behind and names three tables that do not exist, retention's non-customer search is broken by a mangled regex, low feedback does not stop retention messages or open an inbox escalation, and a mangled Graph-version regex rejects the documented META_GRAPH_VERSION. The recommended build keeps everything on existing tables where possible: alter crm_review_requests and customer_feedback for survey kinds, CSAT/NPS and follow-through; route low scores into the existing human_escalations machinery; let approved retention steps carry the same private feedback link; add two migrations (0090 follow-through, surveys, batches, permissions; 0091 external reviews, replies and connections behind an honest 'not connected / not approved' state); and restrict the Performance Analyst to a read-only reputation_review capability, with replies drafted by AI but approved and posted only by a person.

## Risks
- Review gating regression: any future code that selects who is asked, or what link they see, by rating, comment, escalation state, tag or lead score would violate platform policy and consumer-review law. Mitigation is structural (criteria type without such fields, page query takes only org_id, static guard test), not a promise. Whether a person-set retention_paused hold may suppress automated review asks is a policy decision (see founder decisions).
- Outbound webhooks and the n8n/webhook workflow steps carry the rating (webhooks.ts:616-624, reviews.ts:997-1000). A client could build gating in an outside tool. It cannot be blocked in code; the Reviews screen and docs should say what the rules are.
- Provider access: Google Business Profile API access, OAuth verification for business.manage and Meta review permissions can each take weeks and may be refused. I had no network, so the endpoint shapes named in the design (Google accounts/locations/reviews list plus reply update; Facebook ratings/recommendations edge) come from memory and docs/voice-and-reviews.md and must be verified against the providers' current documentation before any adapter code is written. Also confirm each provider's terms allow storing reviewer names and review text outside the provider.
- Public replies are published under the client's name: a wrong or promotional reply, one that confirms the reviewer is a customer or patient (privacy, and the healthcare starter explicitly says not to include health details), one that offers compensation for changing a review, or a prompt-injected draft. Hence version-bound human approval, a posting-time text equality check, and a pure rules module that blocks rather than warns on incentives, links, phone numbers and personal data.
- Shared retention allowance: review requests and every retention program use scope 'retention' (max 4 per 30 days, 72 hours apart, default). Adding surveys and link-bearing steps can starve each other; tests must prove the ordering and the 'waiting' behaviour, and the report must show 'held by frequency limit' separately from 'not sent'.
- A link-bearing retention step is new plumbing in a working engine: the request row must exist in the same transaction as the queued message or dispatch blocks with review_link_unavailable (send.ts:812). Needs a regression test for cancel, draft-for-approval and blocked paths.
- createEscalation returns emails that the caller must send after commit; calling it inside the public feedback transaction without doing so silently drops them. Also verify recordAudit accepts actorKind 'agent' with a null agentInstanceId (createEscalation passes it) in a test before relying on it for system-raised escalations.
- Appointment-based triggers depend on staff marking 'showed' (appointments.manage only). If outcomes are not recorded, no post-service follow-up or review ask ever fires. A daily internal nudge is the honest fix; auto-marking would fabricate outcomes.
- The scheduler has never run in production and Hermes is not provisioned. All new jobs are inert until a founder-approved stage, AI reply drafting needs a configured LLM (honest 'not connected' state), and nothing about reply quality has been evaluated against a real model.
- Two parallel feedback stores: legacy manual retention_accounts feedback and CRM review/survey feedback share customer_feedback; the /retention page averages both. Decide whether to label or split before adding CSAT/NPS numbers so one headline figure is not a blend.
- Erasure and retention of new data: external reviews are public provider data, but the local mirror, drafts and survey comments need a retention period, deletion on disconnect, inclusion in offboarding export and redaction handling. Reviewer names must not be auto-matched to contacts (same rule as webchat decision D2); manual link only.
- Phase 4 social AI drafting is not metered (src/server/social/ai.ts:92-98). If reply drafting copies that file instead of inbox-ai.ts, LLM spend becomes untracked.
- Test churn: tests/crm-reviews.test.ts:603-621 asserts the static 'Blocked' / 'Business Profile API' text; replacing the card with a real status component requires updating that test, and tests/workforce-review-capabilities.test.ts hard-codes the Performance Analyst capability list.

It also leaves crm_form_submissions answers and crm_call_records summaries. Erasure is therefore incomplete for private feedback created by /r/<token>.

## Founder decisions
- Does a person's contacts.retention_paused hold also stop automated review asks (workflow, program, batch)? Recommended: yes for automated asks only, audited with a reason and counted in reports; never any automatic hold based on rating, complaint or escalation. Needs counsel's view on review-platform policy and the FTC consumer review rule.
- Should the owner be allowed to pause review asks to a customer with an open complaint? Recommended: no automatic pause; any exclusion is a manual, audited, individually visible choice (see decision 1).
- Low-score thresholds: keep rating <= 2 (and NPS detractor <= 6) or raise to <= 3; and the acknowledgement SLA (default 24 hours).

- Whether NPS is shown at all (statistically weak for small businesses) or only CSAT, and the minimum sample sizes before any score is displayed.
- Whether agency staff may draft replies on a client's behalf (recommended: draft yes, approve and post never) and whether the agency mirror may see survey comments.

## Recommended design
## 0. Review-gating-safe rules (enforced by code, not copy)

R1. One page, one set of links. /r/<token> renders the business's active destinations in its order for every token, every state (open, closed, expired, after feedback) and every score. loadReviewPage's destination query takes org_id only. A survey request (kind 'survey', CSAT or NPS) uses the same page, so it also shows the links. There is no setting that hides them.
R2. Who is asked never depends on how they feel. Ask selection (manual, workflow request_review, retention step with a feedback link, batch) may use only: a service-completed fact (appointment showed, deal won, customer since), channel and address, service consent exactly 'granted', suppression, the 30-day cooldown, quiet hours and business hours, credits, and a person's explicit per-contact hold. Never rating, NPS bucket, comment, feedback status, escalation state, complaint tag or lead score. Batch criteria are a zod strictObject without those keys; a static test reads the source of src/server/reputation/batches.ts and the ask-eligibility functions and fails if they reference customer_feedback, human_escalations or feedback status.
R3. A low score adds, never replaces. It adds a private follow-up (task, inbox escalation, notification, stopped automatic program messages). The thank-you copy for a low score differs from a high score only by the sentence about the private follow-up; it never asks the customer to wait or reconsider before posting. A test compares the rendered output for scores 1 and 5.
R4. No incentives: pure reviewIncentiveFindings(text) (discount, coupon, free, gift, reward, 'in exchange', 'off your next') blocks saving a review-request template, a feedback_request/service_followup step with a link, and any AI reply draft. Blocks, not warns.
R5. Never fabricate: external_reviews has no insert/update grant and no server action; only syncConnection() writes it from a provider response. Simulated rows exist only when NODE_ENV is not production and carry a visible 'Simulated' badge. Aggregates are computed from stored rows and shown with count, source and 'synced <time>'; provider-reported totals are stored separately (reported_rating, reported_review_count) and shown as 'Google reports N reviews; N synced'.
R6. Replies: AI drafts, a person approves a specific version, a person with reviews.reply_publish posts, and the posted text must equal the approved text (hash re-checked at post time). There is no 'auto-reply' setting.
R7. Customer messages only through evaluateSend. A message carrying a private link additionally requires consent 'granted' on the channel actually used (the same rule review requests already apply) and is refused for suppressed addresses.
R8. Any person-set hold (contacts.retention_paused) is audited with a reason and counted in the report as 'held by a person' so a pattern is visible. Whether it applies to review asks is founder decision 1.
