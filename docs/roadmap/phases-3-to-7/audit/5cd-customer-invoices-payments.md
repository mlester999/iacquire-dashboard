# Phase 5C/5D: customer invoices and customer payments (the client's own customers), kept separate from iAcquire's own billing; verified revenue for the Lead Sources report

## Summary
Nothing for customer invoices, customer payments, PayPal or Stripe exists in this tree or in any of the 65 refs I searched (git grep on every head and remote for invoice, paypal, checkout_session, payment_intent). What exists is iAcquire's own billing: a PayMongo hosted checkout and signed webhook for credit top-ups and the setup fee (src/server/billing/*, migration 0018, tests/billing*.test.ts), credentials held in global env secrets, and a manual maintenance-payment record. That code is sound at the signature, replay and amount-check level, is tested with mocks only and has never touched a PayMongo account. Its pure pieces (signature verification, event parsing, checkout host allowlist) are reusable as-is. Everything else must be built fresh: a decimal-safe invoice model (no currency-exponent helper exists), per-customer-of-client provider connections, a per-tenant webhook endpoint, reconciliation, refunds netting, reminders through the existing consent-gated send chain, CRM/Automation events, and a verified-revenue feed. The attribution report is ready for that feed: SourceRow.verifiedRevenue is hard-coded null at src/server/attribution/report.ts:116-118 and its tests assert the null. I also found one real monitoring gap in the existing webhook code (error outcomes can never persist, so its alarms are dead) and an unresolved credential-storage policy conflict that the founder must settle before client payment secrets are stored. All provider work will be locally tested only; real PayMongo/PayPal behaviour is blocked on sandbox/test credentials that the founder must supply.

## Risks
- Marking an invoice paid too early: a provider return URL, PayPal CHECKOUT.ORDER.APPROVED, a PayMongo checkout_session.created, or a pending payment must never create a succeeded payment. Only a verified success event (or an authenticated re-fetch of the payment from the provider) with matching amount, currency, reference and mode may.
- Forged, replayed, reordered or cross-tenant webhooks: tenant must come from the connection key in our records, the signature from that connection's own secret, and the invoice from our stored attempt, never from the event body. A validly signed event for org A that names org B's invoice must be inert.
- Money arithmetic: floats, a /100 assumption (formatMinor), mixed conventions (micros, cents, numeric(14,2)), tax rounding and tax-inclusive pricing. Use bigint minor units, an explicit currency exponent table and BigInt math with one documented rounding rule.
- Double counting verified revenue (webhook + reconciliation poll + manual entry for the same money): unique (connection_id, provider_payment_id) and a rule that a manual payment cannot be recorded against an invoice that has an open provider attempt for the same amount without an explicit override.
- Refund handling: refund before payment event, partial refunds, refund greater than payment, refunds on manual payments, chargebacks. Refunds must reduce net revenue and never silently re-open an invoice or a won deal.
- Overpayment and duplicate payment (two checkout attempts both succeed): record, flag, notify, never auto-refund, never inflate revenue beyond what was received.
- Secrets that can move money: a pasted PayMongo secret or PayPal client secret is full-account access unless the provider offers restricted keys (unverified). Storage policy conflict (Vault vs app-sealed) is unresolved; leaking a key into logs, notifications, audit metadata or AI context must be tested against.
- Raw card data: only provider-hosted checkout. Add a schema guard test (no column named like card/pan/cvv/expiry) and a Luhn check on free-text invoice fields; never persist webhook bodies (store a sha256 and the normalized fields only).
- Reminder consent: evaluateSend refuses a first service message to a contact with no consent record and no inbound message, so many reminders will be blocked. That is correct; the UI must show the reason, not hide it. The pay link is a bearer secret and must never be stored in message bodies, threads, exports or AI context (placeholder + maskCustomerLinks).
- Public pay page abuse: token brute force (use 43-char HMAC tokens, hash stored), enumeration, amount tampering (amount always computed server side from balance), checkout flooding (one open attempt per invoice, rate limits), CSP form-action 'self' (src/proxy.ts) means the pay button must call fetch then navigate, not rely on a form post redirect.
- Immutability and numbering: edits after issue, number gaps or duplicates under concurrency, voided numbers reused. Number is assigned inside the issue transaction from a locked counter; content_hash is frozen at issue.
- Attribution misstatement: cohort timing (revenue after the cost period), tax included in revenue, test-mode and manual payments, deals on merged contacts, currency mismatch between cost and revenue (no FX is ever invented), payments with no contact.
- Legal/tax: the module must say 'Invoice' and show only tax lines the owner enters; no automatic tax determination; no claim of BIR/VAT compliance; erasure requests vs financial-record retention need counsel.
- Scheduler dormancy: overdue flags, reminders and reconciliation polling run only when the founder starts the scheduler stage; the UI must say 'checked when the scheduler runs' and never imply live monitoring that is not running.
- Provider contract drift: nothing has been exercised against real PayMongo or PayPal. Existing paymongo.ts calls /v2/checkout_sessions, which I could not confirm offline. Treat every provider claim as 'built, locally tested' until a sandbox run is recorded.
- Cross-contamination with agency finance: customer payments must never appear in getFinancialReport (src/server/billing/finance.ts), payments, credit_ledger_entries or the agency 'money received' line. Add a test that seeds a customer payment and asserts the agency statement is unchanged.
- Next.js in this repo is a non-standard version (AGENTS.md): read node_modules/next/dist/docs for route handler params (they are Promises here), after(), and public route conventions before writing the webhook and /pay routes.
- Repository plumbing that breaks silently: PERMISSION_MATRIX/database parity test, notifications_kind_check rewrite (use the 0089 live-constraint DO block), conversation_messages_scope_check, credential provider check constraints, MIGRATION_PREREQUISITES, crm-migrations test list, rollback that refuses while rows exist.

## Findings in existing code
- [medium] src/server/billing/payments.ts:136 handlePaymongoWebhook inserts the payment_webhook_events receipt and processes the event inside one withSystem transaction. If processing throws, the receipt rolls back, so outcome 'error' (and a lingering 'received') can never be stored; nothing in src writes 'error'. The alarms that read them (src/server/ops/collectors.ts:143 'payments:webhook-errors', collectors.ts:153 'payments:webhook-stuck', src/server/aqi/ops/tools/health.ts:70-71) are therefore unreachable, and a failed paid-event is visible only as an HTTP 500 and a console line. Do not copy this shape for customer payments: commit the receipt first, process in a second transaction, mark 'error' in a third.
- [medium] src/server/social/credentials.ts:8 Policy conflict on stored secrets: supabase/migrations/0010_secure_integrations.sql (lines 1-2) and src/server/security/credentials.ts:96-97 say new credentials live in managed Supabase Vault and refuse app-owned ciphertext in production, while Phase 4's social_accounts.credentials stores AES-GCM ciphertext under APP_ENCRYPTION_KEY with no Vault reference (encryptSecret in sealCredentials). Rotating APP_ENCRYPTION_KEY orphans those tokens, and the same shortcut would be wrong for payment keys that can move money. The founder should settle which rule wins before customer payment secrets are stored.
- [medium] src/server/messaging/contacts.ts:235 moveContactReferences uses a hard-coded table list for contact merges; any new table with contact_id (customer_invoices) is left on the soft-deleted contact, so verified revenue and invoices would follow the wrong contact in the attribution report. Both lists must be extended with the new tables.
- [low] src/lib/billing.ts:58 formatMinor divides every currency by 100 (and usdToChargeMinor assumes 2 minor-unit digits). ## Founder decisions
- Collection model: confirm the client's own PayMongo/PayPal account (recommended; iAcquire never touches customer funds) versus iAcquire collecting on the client's behalf (not recommended: payout, KYC, tax and liability exposure, and it blurs agency revenue with client money).
- Provider scope for v1: PayMongo and PayPal as selected. Confirm the currencies your clients invoice in (PayMongo appears PHP-only in this codebase, so USD invoices need PayPal), and that no FX conversion is ever done on customer invoices.
- Entitlement placement (no new price invented): include invoicing and manual payment recording with the $1,499 implementation, or gate payment collection or reminders behind the $299/month Managed Maintenance + Automation Studio plan. Recommendation: core invoicing included; triggers are not plan-gated; premium steps stay gated as today. Also confirm iAcquire takes no fee or cut from customer payments.
- Credential storage for money-moving keys: Supabase Vault (matches the 0010 policy but needs an owner-authorized save path and new provider names) or the Phase 4 app-sealed column (simpler, conflicts with the policy, tied to APP_ENCRYPTION_KEY). Recommendation: Vault.
- Credentials and accounts you must supply to go beyond simulated tests: PayMongo test secret key + webhook secret (already an open item in docs/finance-and-billing.md) and a PayPal developer sandbox REST app (client id/secret) with a webhook id; later, per pilot client, their own live accounts and written consent. Confirm in the sandbox whether PayMongo or PayPal offer restricted-scope keys, because otherwise a pasted key is full account access.

- Whether manually recorded payments (bank transfer, cash) count as 'verified revenue' in ROI. Recommendation: no by default, shown separately, owner may opt in with disclosure.
- Whether ROI revenue excludes tax collected (recommended) and whether it is cohort revenue to date or revenue received within the report period (recommended: cohort to date, labelled).

- Release approvals as always: nothing pushed, no hosted migration 0090, no scheduler start (overdue sweep, reminders, reconciliation) and no live provider call without your explicit approval.

## Recommended design
## Principles
* **Separate domain.** Prefix everything `customer_` (customer = the client's own customer; `client` already means the tenant and `payments` is agency billing). No writes to `payments`, `payment_webhook_events`, `credit_ledger_entries`, `billing_accounts` or `agency_finance_entries`; no reads of them either.
* **Collection model: the client's own provider account.** The client owner pastes their own PayMongo/PayPal credentials; funds settle to them; iAcquire never holds customer money (no payout, KYC or tax exposure, agency revenue stays separate). iAcquire-collected funds are not recommended.
* **Paid means a verified provider fact.** Evidence class stays 'Built / Verified Locally (simulated + signed fixtures)' until a sandbox run is recorded.
