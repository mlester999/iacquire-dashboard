# Phase 7C/7D/7E audit: client onboarding journey, personalized demo and sales funnel, billing and subscription lifecycle (worktree .data/wt-phases-3-7, branch feat/phases-3-7 @ 9a495af)

## Summary
Onboarding (7C) is mostly real and well tested: client creation is staff-only (createClientTenant), accounts come from hashed single-use invitations that prove the email, one adaptive 60-question questionnaire prefills and persists per answer, submission builds six versioned employee configs, and employees stay "Setup required" until a live Hermes health check passes (tests/client-onboarding-acceptance.test.ts asserts none is online and no profile is mapped). The biggest control gap is that no code path reads billing_accounts.setup_payment_status to gate anything: requestProvisioning, activateSetup (a test activates a client with the default not_invoiced status) and maintenance eligibility all ignore payment, and the unmerged automated Hermes provisioner on codex/client-ai-onboarding would claim jobs for unpaid clients. The demo funnel (7D) does not exist in any of 65 refs or 40 worktrees (including uncommitted files): Membership.isDemo/organizations.is_demo is only a flag for seeded fictional sample workspaces set by dev seed scripts, and the only funnel code is /get-started writing access_requests plus a 2026-10-19 gap-audit doc (docs/sales-and-demo-funnel-audit.md) whose plan is still valid and whose Phase 1 payment gate was never built. Billing (7E) has a solid PayMongo credit/setup-fee engine (signed webhook, event ledger, amount/currency/livemode checks, idempotent credits, tests with mocks only, no keys configured, setup-fee checkout has no UI) and a careful manual maintenance lifecycle (agency-verified activation, past-due, grace, expiry, premium-only pausing; core CRM/employees are never gated, tested), but PayPal has zero code anywhere, nothing is automatic or recurring, refunds and manual receipts never reach the payments table or finance report, and paid_through_on is never enforced. Recommended order: payment clearance gate plus a manual-payment/waiver record (migration 0090) first, then a shared entitlement helper and renewal reminders, onboarding gaps, the demo funnel (0091), purchase intents with verified-payment tenant provisioning (0092), and PayPal last because it is blocked on an account.

## Risks
- Gate rollout: production had 3 organizations (1 active) and 0 maintenance plans per docs/automation-studio/production-audit-2026-10-22.md (not re-verified, no network). The payment gate must be introduced with an explicit, audited backfill (waive existing active clients with a reason) or the live client stops being able to provision or activate; it must never retroactively disable employees of an activated client.
- If codex/client-ai-onboarding (automated Hermes provisioner) merges before the gate, unpaid clients get real Hermes profiles automatically (cost and abuse). The predicate has to be in requestProvisioning AND in the claim SQL.
- Relaxing payments.provider and adding manual rows touches the money table and the reports built on it (finance.ts, getAgencyBillingOverview). Existing tests/billing.test.ts must pass unchanged; add a rollback and rehearse on embedded Postgres.
- Scheduler has never run in production (needs CRON_SECRET + SCHEDULER_ENABLED, Hobby plan caps cron at daily). Demo expiry, renewal reminders and retention must also be enforced at read time (time-aware checks, like studioEntitlement), not only by jobs.
- Public unauthenticated AI is a cost and abuse surface: needs per-prospect, per-IP, per-day platform caps, a global kill switch (env + setting), message length caps, and an honest 'AI not connected' state when resolveLlmConfig is null. Prompt injection from name/business fields must be fenced.
- Prospect personal data (name, work email, transcripts) needs notice, retention and erasure; legal wording for demo terms and marketing consent is unreviewed (founder/counsel).
- Email deliverability for prospect verification is unproven (Resend reported on in prod, untested for this flow); unverified prospects must get no AI and no data. Verification must be a POST confirm so mail scanners cannot burn the link (same reason as confirmEmailLinkAction).
- Demo conversion hazard: any code path that creates users/organizations/invitations from prospect activity would violate 'never accidentally convert'. Keep demo tables free of FKs to users/org except converted_org_id set only in the explicit Super Admin or verified-payment transaction; add a static + DB test.

## Recommended design
## Principles (invariants every milestone keeps)
1. Core stays ungated. The only premium surface is Automation Studio (+ managed media storage). Lapse, refund or non-payment never touches CRM, inbox, six employees, website, booking, social text posts. Add one test matrix that proves it.
2. Payment is evidence, not a click. Anything that provisions cost (Hermes profile jobs, activation, plan start, tenant creation from a purchase) requires a cleared payment: a paid row in `payments` (provider paymongo/paypal verified by signature, or provider 'manual' recorded by a Super Admin with reference + note) or an explicit audited waiver. No UI text may say a payment was detected unless a provider webhook did it.
3. Demo visitors are prospects, never users. No `users`, `auth_*`, `organizations`, `organization_memberships`, `invitations` rows are created by anything in the demo module.
4. Everything additive: migrations 0090/0091/0092, select-only RLS grants, composite org FKs where an org exists, rollbacks in supabase/rollbacks/, rehearsal like scripts/rehearse-phase3-migrations.mjs. Nothing applied to a hosted DB or enabled without approval; all new switches default off (`DEMO_ENABLED`, `demo_settings.enabled`, `PAYPAL_*` unset).
