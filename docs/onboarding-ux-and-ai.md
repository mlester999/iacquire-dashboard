# Onboarding UX and writing assistance implementation

Based on master `7e6a181`. Local branch: `codex/premium-onboarding`. No push, deployment, production configuration changes or live model calls.

## Interface

1. **Navigation:** Back and Continue share one row. Phones/tablets use a fixed bottom action area with safe-area padding and VisualViewport keyboard offsets. Content reserves bottom space and inputs/errors have scroll margins. Submission and navigation use a synchronous lock to prevent duplicate requests. Review ends with the approval action, gated by the existing review and confirmation requirements.
2. **Save & exit:** One action in the upper header, connected to the existing serial save pipeline. It waits for persistence and preserves the exact resume position. Invalid local edits stay visibly unsaved and block exit; older queued/in-flight values cannot masquerade as the current saved answer. Failures keep the user on the question.
3. **Progress:** A "Built around you" panel above the question card, dark navy in both themes (`.onboarding-stages` in `globals.css`). It is the only place showing the current section, the question position ("Question N of M"), the answered percentage and the save state; the card itself only says Required/Optional. A six-segment meter (the `Setup progress` progressbar) fills each section by its real answered share, and six stage tiles (Business, Goals, Voice, Sales, Knowledge, Review) show complete (check), current (accent tile) and remaining states. Phones get a 3×2 tile grid with labels only; 640px adds per-stage status ("4 of 12", "Complete"); from 768px the tiles sit in one row aligned under their meter segments; desktop adds the section description and a larger heading. Tiles jump to that section's next open question, as before. All figures come from `computeProgress` and the existing conditional totals. A brief welcome title appears on the first question.
4. **Questions:** Smaller card padding and headings, compact tappable options, shorter description help and examples behind disclosure. Inputs retain question limits and use 16px text on phones. Existing question definitions, branching and approval semantics remain authoritative.

## AI behavior

5. **Existing integration:** Production already called `llmComplete(resolveLlmConfig())`; no deterministic fallback was found there. The old prompt had a limited universal fact set, omitted current wording, and supplied no clarification mechanism. The implementation keeps this shared provider client/resolver. Eligible agency Integrations configuration supplies the provider/API format/model; the existing environment fallback remains unchanged. No new credentials or hardcoded model are introduced.
6. **Context:** Each of the 12 currently AI-enabled questions has its own intent and field allowlist. Context can include relevant saved answers, current wording, at most two explicit optional clarifications, relevant approved company knowledge, and a recent same-company website snapshot. Saved answers take precedence over older knowledge. Unconfirmed policies, unrelated knowledge, contact fields and other tenants are excluded. Clarifications are request-only until their resulting wording is accepted into an answer.
7. **Grounding:** Instructions treat all company/website text as untrusted data. Output must match the field shape/length and cite exact quotes from available sources. Sparse descriptions receive a preliminary draft and optional questions rather than invented services or customers. Additional vocabulary checks reject new content details; these conservative checks can also reject unfamiliar paraphrases. Prices and FAQs keep their website-only restriction. These are safeguards, not independent factual verification; the owner still reviews drafts.
8. **Approval and controls:** Generated output stays in a separate preview. Use suggestion, Edit, Regenerate, Dismiss and optional detail refinement preserve the existing answer until explicit acceptance. Sensitive policy wording retains the existing separate confirmation gate. Disconnected/provider-failure states have actionable feedback and never fall back to a template. Requests support cancellation, a 25-second timeout, bounded input/output/tokens, existing 25/hour organization usage limits, an 8/minute viewer burst limit, identical-request deduplication and a short context-bound cache. Audit records include model/source metadata without credentials or company text.

## Verified results and release status

9. **Automated:** 94 tests passed across onboarding engine/persistence, save pipeline, UI interactions, assistance service, HTTP endpoint and shared provider transport. TypeScript (application and scripts), targeted ESLint and diff whitespace checks passed. Provider calls are mocked in these tests; they do not establish live model quality.

   **Browser:** 52 Chromium checks passed using the actual components and app CSS with the clearly labelled existing local-preview mocks. Light/dark widths: 320, 360, 390, 430, 768 and 1440px. Checks cover row alignment, touch targets, overflow, fixed footer, phone input font size, preview editing/acceptance, save failure/retry, back/continue, refresh/resume and simulated visual-viewport keyboard conditions. Screenshots were visually inspected. Native Android/iOS keyboards and physical devices were not tested.

   Reproduce: set `PLAYWRIGHT_MODULE` to an installed Playwright `index.mjs`, then run `node scripts/onboarding-browser-qa.mjs`. Evidence is written to `.data/onboarding-qa/report.json` and four light/dark phone/desktop PNGs.
10. **Remaining:** The isolated development runtime refused a remote production database lookup; its guard was left intact. Consequently the currently connected hosted provider/model and live generation quality are **not verified**. No Vercel Preview or production-equivalent build was run. The change is ready for an authorized Preview and live-provider acceptance check before a production release. Existing Hermes policies, AI employee configurations, workforce execution, CRM rules, customer data and schedules were not changed.
