# AI employee chat and workforce management

This page records the AI Workforce experience built on the existing iAcquireOS foundations: one employee
registry, one chat backend, versioned configuration, knowledge, approvals, audit and health checks. It does
not add a second employee registry or a simulated chatbot.

## Two isolated workforces

| Scope | Who manages it | Where it lives | Isolation |
| --- | --- | --- | --- |
| iAcquire internal | Agency super admin | The `iacquire-qa`/agency organization's six `agent_instances` rows | The agency organization is its own tenant. Client users are never members of it, and client profiles may not use `iacquire-*` names (database trigger). |
| Client | Business Owner / Manager (subject to permissions) | Each client organization's own six employee rows | `org_id` on every employee, conversation, run, knowledge row and config version; composite `(id, org_id)` foreign keys; RLS; server ownership checks. |

`Super Admin` access to a client's workforce remains through the existing audited client administration
screens, not through the client portal.

## Internal workforce access

`src/server/workforce/agency.ts` prepares the agency workspace when a super admin uses the admin area:

- finds the active agency organization;
- ensures the six known role records exist without renaming or overwriting an existing identity;
- creates or raises the super admin's **owner membership in the agency organization only** and writes an
  audit event the first time;
- `GET /admin/workforce/open?role=<slug>` switches the active organization to the agency organization and
  redirects to the existing `/chat/<slug>` screen, or to `/workforce/<slug>?tab=configure` when
  `&to=manage` is present. The configuration screen is the normal employee detail page; it now also
  accepts the internal agency organization for a Super Admin, so activation step 1 (saving each internal
  employee's initial configuration) uses the same reviewed form as a client employee. It is
  super-admin-only and records an audit event.

The admin employee page `/admin/workforce/[slug]` shows the real identity, runtime, connection evidence,
configuration summary, SOUL.md, knowledge counts, approvals and recorded runs, with health-check and
pause/enable controls.

## Chat

The existing chat pipeline is reused (`src/server/chat/service.ts`, `/api/chat/send`,
`/api/chat/runs/[id]/stream`, `/api/chat/runs/[id]/stop`). It provides:

- real provider runs with SSE streaming when the provider supports it;
- a non-streaming fallback through the documented `GET /v1/runs/{id}` when the provider advertises
  `run_submission` without `run_events_sse`: the UI shows an honest “waiting for the complete response”
  state and renders the real final output once;
- an honest thinking/processing state, cancellation, timeout and reconnect after reload;
- persisted conversations and messages with private-per-user RLS;
- new, resume, rename, delete (with confirmation), search and one page of older-message loading;
- Markdown with raw HTML disabled and only safe links rendered;
- copy, regenerate/retry, scroll-to-latest only when the reader is at the bottom;
- responsive layouts, keyboard composer and labelled controls.

The chat stream is server-side: provider credentials never reach the browser.

## Employee profile and instructions

The employee detail screen (`/workforce/[slug]`) now exposes:

- **Overview**: identity, assigned organization, provider runtime, enabled state, last recorded activity,
  connection evidence, tools and safeguards.
- **Configure**: versioned identity, tone, language, role answers, rules, tools and approval preference,
  plus **Test this draft**.
- **Instructions & SOUL**: the instruction hierarchy, the generated SOUL.md, the exact applied
  instructions, memory/retention evidence, usage, and version history linking to rollback.
- **Knowledge**: employee notes and reference documents.
- **Version history**: every change, who made it, risk flags and restore (creates a new version).
- **Activity**: recorded runs, status, tools and tokens.

### SOUL.md and the instruction hierarchy

SOUL.md is generated by `src/server/workforce/provisioning.ts` for the Hermes administrator. The verified
Hermes API has **no endpoint that writes a profile's SOUL.md**, so the portal does not offer a save button
that would only change a database row. The UI states this plainly.

What is editable is the versioned per-run configuration. The order sent to Hermes is:

1. employee identity and personality settings;
2. business context and role answers;
3. organization knowledge, employee notes and reference documents;
4. the immutable iAcquire policy, always last.

Client text is quoted as `<client_context>` and cannot grant tools, bypass approval or cross tenants.
Risk-looking text is held for agency review rather than applied.

## Employee knowledge

Migration `0045_ai_workforce_experience.sql` adds (renumbered from 0041 after the hosted migration
history showed 0041–0044 already used by CRM migrations):

- `employee_knowledge_entries` (title, content, status, version, risk flags, author, last-used evidence);
- `knowledge_documents.agent_instance_id` (null = shared library, otherwise one employee);
- `knowledge_documents.risk_flags` and `last_used_at`.

Behavior:

- Owners and Managers with `knowledge.edit` can add/edit/archive notes and assign, upload or share
  documents. Anyone with `knowledge.view` can read.
- A note or document with prompt-injection-looking text is stored but **not** given to the employee until
  iAcquire reviews it; the UI marks it `In review`/`Held`.
- Retrieval uses the same `compileKnowledgeSections` function as the run instructions, so the UI reports
  exactly which sources are included and whether the character budget truncated them.
- `last_used_at` is written only after `POST /v1/runs` is accepted, not when a row is saved.
- Migration `0046_knowledge_document_extraction.sql` adds bounded extraction states and evidence:
  `processing`, `ready`, `failed`, `unsupported`, `processing_detail`, `extraction_method` and
  `processed_at`.
- Selectable-text PDF and Word (.docx) documents are extracted locally without a paid service or OCR.
  Flate-compressed PDF content streams and WordprocessingML paragraphs/tables are supported. PDFs
  using unsupported filters, encrypted content or exotic object compression may be reported
  `unsupported`/`failed`; upload a text export in that case. The original file remains downloadable in
  every state.
- Encrypted PDFs, scanned/image-only PDFs, malformed archives, ZIP64 Word files and exotic PDF filters
  are reported as `unsupported` or `failed` with a plain-English reason; they are never retrieved. OCR
  is **not** implemented or claimed.
- Extracted text is scanned in full for prompt-injection patterns. Held documents are stored but not
  given to the employee.
- A document or note is scoped by `org_id` and `agent_instance_id`; the composite foreign key makes
  cross-tenant assignment impossible even with a forged identifier.

## Draft testing

`src/server/workforce/preview.ts` and `/api/workforce/preview` run an unsaved draft:

- the draft is validated and compiled with the protected policy;
- summary, changed fields, warnings and knowledge counts are returned;
- when a provider is connected, a real Hermes run starts with a unique `preview-*` session and
  `iaq:preview:*` memory scope;
- no conversation, message, run row, usage event or configuration version is written;
- the production employee's active configuration is untouched;
- the provider's own security gate (verified tool inventory) still applies; an unavailable provider is
  reported honestly rather than simulated.

## Memory

Conversation history is persisted and private. Long-term memory is kept by Hermes inside the employee's
own profile with `X-Hermes-Session-Key: iaq:<org>:<role>`. The verified API has no memory read/edit
endpoint, so the UI:

- shows the scope, conversation/message counts and retention;
- shows recorded memory tool activity where it exists;
- states that inspection and editing are unavailable;
- never claims a memory editor changed a profile.

## Health, usage and audit

- Health is evidence-based: an employee is online only after the authenticated capabilities, profile
  identity and toolset checks pass; a saved key alone is not enough.
- A health check writes the employee's status, inventory attestation and integration state, so it
  requires `agency.workforce.manage` and the existing assigned-client scope. Super Admins keep access;
  internal system refreshes (chat status rechecks and the setup engine) do not depend on an agency
  permission. Read-only staff can still view the workforce and its last recorded evidence.
- The employee view shows last check, detail, tokens, runs, failures, tool steps and average latency.
- Provider cost is not reported by Hermes, so no estimate is shown.
- Configuration changes, knowledge changes, draft tests, internal-workspace access, publishing and
  rollback are audited.

Local automated tests (`tests/ai-workforce-experience.test.ts`,
`tests/knowledge-extraction.test.ts`, `tests/knowledge-migration-0045.test.ts`,
`tests/knowledge-migration-0046.test.ts`, `tests/knowledge-migration-hosted-compat.test.ts`):

- employee notes and document scoping, retrieval and last-used evidence;
- selectable PDF (plain and Flate) and DOCX extraction, employee/shared scoping and chat-pipeline
  retrieval of the extracted text;
- encrypted, scanned, malformed and empty documents fail honestly and are never retrieved;
- migration 0045/0046 rollback safety and refusal while data depends on the newer schema;
- prompt-injection hold;
- cross-tenant employee/note/document denial;
- draft preview compiles and runs through the mock provider without writing production rows;
- internal agency workspace preparation is idempotent and preserves existing identities;
- super admin internal chat works through the normal chat backend;
- owner/manager/working-staff access and the viewer/configuration denials;
- non-streaming run-status polling fallback;
- diff output and failure honesty.

Browser QA (`scripts/workforce-browser-qa.mjs`, synthetic records only, isolated embedded database). With
the QA server stopped:

```bash
npm run workforce:qa:seed
npm run workforce:qa:server        # isolated server on http://localhost:3230
PLAYWRIGHT_MODULE=<path-to-playwright-core/index.mjs> npm run workforce:qa
```

Results:

- 10 signed-in pages at 1440 px and 390 px, both scopes;
- 6/6 interactions: internal chat, search/rename/delete, older messages, knowledge, instructions,
  draft-test dialog;
- real extracted PDF and DOCX files visible in the Knowledge tab with `PDF text` / `Word text`
  provenance badges;
- 0 horizontal overflow, 0 axe-core violations, 0 console/page errors, 0 failed requests.

**Verified live, read-only:** gateway authentication, profile identity for the six internal employees,
capabilities and the actual restricted-tool exposure. **Not verified:** a real model response, a live
client profile, provider costs, or hosted deployment. The complete-tool-inventory gate blocks live runs
until the gateway administrator supplies a supported complete inventory contract and disables the
dangerous profile tools. Draft-test and chat screens were browser-checked with synthetic online states
and no provider; the automated provider path uses the local mock gateway and is labelled as such.
