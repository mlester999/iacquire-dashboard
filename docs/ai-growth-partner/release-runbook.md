# AI Growth Partner release runbook

Use this runbook with the [completion tracker](MASTER_COMPLETION_TRACKER.md) and [migration strategy](migration-strategy.md). Record one candidate SHA, the environment, the test data scope, and the evidence for each check. Production changes, hosted migrations, customer cutover, paid inference, external provider calls and outbound messages require separate owner approval.

## Prepare the release

1. Compare the candidate and the remote release branch with `git ls-remote origin refs/heads/master refs/heads/codex/growth-partner-release-candidate`, then inspect the candidate diff and migration ledger. Confirm the candidate's branch-specific `git.deploymentEnabled` setting and the linked project's production branch and environment bindings before pushing. After the first push, record the receipt for both GitHub Actions workflows. A docs-only update may leave the Hermes path filter unchanged. Stop and notify the owner if the live application or any server changes during this work.
2. Run app and script typechecks, ESLint, full regression, browser and access-control checks, a production build and the pinned two-tenant Hermes acceptance on the same source SHA. Keep heavy jobs serial on a constrained host. Record actual failures and skips, and keep synthetic model and data evidence distinct from provider or hosted acceptance.
3. Rehearse schema apply, rollback, replay and backup restore with the embedded disposable database.

   ```sh
   npm run rehearse:migrations -- --report .data/growth-partner-release-migrations.json
   node node_modules/vitest/vitest.mjs run tests/migration-prefixes.test.ts tests/growth-partner-migration-inventory.test.ts tests/growth-partner-schedule-migration.test.ts tests/growth-partner-migration-candidate.test.ts tests/growth-partner-migration-action.test.ts tests/growth-partner-migration-plan.test.ts --maxWorkers=1
   ```

4. Before a hosted migration request, compare the actual ledger to the rehearsed schema and inspect the database target, pending migration names and table locks read-only. Inspect `to_regclass('public.schema_migrations')` in a read-only transaction before selecting ledger entries. The app runner's `--dry-run` can create a missing ledger, so use it only on a disposable copy or as part of an explicitly approved hosted operation. The recovered chain retains AQi guidance at `0136_ai_growth_partner_conversation_first_aqi_guidance`. Candidate migrations follow at 0137–0146, including idempotency, saved chat previews, stored product copy, sender verification, organization creation, migration plans, workspace OAuth, migration preparation, the FSA directory source and connected knowledge. The actual target determines which files are pending. Investigate any divergent ledger entry before changing it.
5. Rehearse restore on a throwaway database of the target PostgreSQL major version before requesting hosted write approval. If a client-data backup is in scope, get specific approval for the data export and restore test, keep the encrypted dump outside the repository, and record the retention owner and verified restore result. Apply each approved migration with the runner's exact `--only <migration_name>` selection. Verify the schema and ledger change, tenant row preservation and access checks before requesting the next action.

## Existing-tenant preparation

| Step | Current code and expected evidence |
| --- | --- |
| Inventory | In Super Admin → Clients → client detail, review previous profiles, active and pending config, same-tenant credential references, verified health, knowledge release states, conversation/history counts, approvals, connected integrations and permissions. The inventory returns metadata and counts. Keep credentials and customer content out of the release record. |
| Dry-run | Select the schedule reconciliation preview. This requires Super Admin and `agency.workforce.manage` for that client. Capture enabled and due schedules, timezone, cadence, eligible capability mapping, existing Partner schedule matches and each open legacy work item's status, idempotency key and schedule link. Repeat immediately before any approved transition to catch changed work. |
| Validate the boundary | The synthetic inventory and preview tests use another workspace to prove scoping and verify the recorded legacy rows stay intact. The preview writes nothing. A policy match in the preview does not certify runtime or tool readiness. |
| Prepare a candidate | On synthetic data, call Prepare migration candidate twice. The first call creates one unbound `migration_required` identity and one audit event. The second returns the same identity. Confirm zero Partner runtime, Brain version or permanent conversation changes, with legacy profiles, schedules, jobs, approvals and integrations preserved. Partial legacy sets or existing incompatible Partner setup stop this operation. A real client requires approval for this identity write. |
| Stage and review a plan | On the synthetic tenant, save a Business Brain draft, finish retained source reviews and preview the migration plan. Stage only the exact preview digest. Verify the owner’s decision and the same digest in the audit record. Change a schedule or saved Brain version and verify approval refuses until restaged. Replacing a plan preserves the old receipt. |
| Apply approved preparation | On the same disposable tenant, refresh the approved plan as the scoped Super Admin and select **Apply approved preparation**. Verify the exact approved Brain is active on the unbound Partner and the six profiles, current actor, conversations, jobs, provisioning queue and runnable schedules are unchanged. Repeat the request and verify the candidate runtime and disabled schedule IDs are stable. Verify owner withdrawal closes the receipt and restores only the Brain pointer installed by this step. |

The current workflow ends with an applied Business Brain, a reserved local runtime identity and disabled schedule mappings. An owner-reviewed cutover needs separate acceptance in an isolated tenant before it is offered to customers. For each client, record a dated inventory and the prior schedule/permission state. Get explicit agreement on Business Brain provenance and corrections, capability permissions, retained knowledge, unresolved approvals and each schedule mapping. Provision a tenant-isolated runtime with fresh credential references and verify the permanent conversation, approval gates and tenant denials. Resolve all conflicting jobs and matching schedules, then pause old schedules and drain live leases before enabling any replacement. Validate repeated jobs and restart recovery without duplicating records. Retain legacy history and key identifiers, and request separate approval before any old profile is revoked.

## Scheduler and outbound gate

Keep `OUTBOUND_MESSAGING_ENABLED=false` during rehearsal and rollout. In development use the captured email provider and mocked provider transports. Verify approved drafts remain unsent, due or retried messages make zero provider calls, and authentication and account-security email remain available. Keep external CRM writes, calendar sync/write-back, payment writes and deployment-specific workflow switches disabled unless their exact test scope is separately approved.

On a synthetic database only, exercise authenticated `POST /api/internal/tick` with `SCHEDULER_JOBS_ONLY=aiWorkRecovery,aiWorkRunQueued,aiWorkSchedules` and known read-only schedules. Use isolated test overrides for `SCHEDULER_ENABLED` and `WORKFORCE_SCHEDULES_ENABLED`. Prove one instance per occurrence across a repeated tick, failed and cancelled state, lease recovery, paused schedules producing no jobs, foreign-tenant denial and matching audit evidence. The allowlist applies to tick only. Leave `WORKFORCE_WORKER_ENABLED` off and review provider webhooks and request-time execution separately. The canonical checks are in [the scheduler runbook](../production-scheduler.md) and `tests/workforce-queued-runner.test.ts`. The loopback Next.js harness checks the HTTP and restart behavior against a fresh database of fictional tenants with provider sockets blocked. Run `node scripts/workforce-scheduler-http-qa.mjs` with a free `CRM_QA_PORT`. A hosted or production scheduler gets its own approval with named jobs, stage duration, time limit and recorded stop procedure.

## Recovery and rollback

- Stop and report any unexpected production or server change. Each authorized action must record the UTC timestamp, exact command or click, target, result and evidence. Use a forward-fix commit on the current production lineage for application recovery and get approval for its release. Redeploying an older deployment rolls back live code and is prohibited.
- For an approved tenant cutover recovery, pause replacement schedules and confirm no active lease remains. Reconcile any pending approvals and side effects against the migration report before requesting individual state restorations. Restore only prior verified settings, preserve both histories and append the authorized recovery event. Never reuse credentials across tenant runtimes.
- Keep additive schema in place while fixing application behavior. A schema down requires a separate rehearsal and approval. Guards protect task keys (`0137`), saved previews (`0138`), verified sender proof (`0140`), workspace creation keys (`0141`), migration review and preparation history (`0142`, `0144`) and connected knowledge history (`0146`). Review how `0139` restores seeded copy while preserving custom edits. When a down guard fires, evaluate a forward fix that preserves the records.
- A restore from the verified snapshot is a last resort with a fresh impact review of every intervening write and separate restore approval. Record the approved replay scope and recheck tenant isolation, integrity, security and billing state before reopening traffic.
