# CRM performance at realistic scale

Status: **measured locally, PGlite in-memory, indicative only.** The historical RLS timings below are from the earlier 0040 helper
model and do not benchmark the final 0050 rewrite. Every number on this page comes from the embedded PGlite database
(PostgreSQL 18.3 compiled to WebAssembly, single connection, no parallel workers, running inside the test process). Hosted Postgres has a
real buffer cache, parallel query and a network hop, and may run a different major version, so absolute times will differ. What carries
over is the plan shapes, the indexes each call scans, the number of statements per call, and the relative cost of one approach against
another. Migrations `0038_crm_performance.sql` and `0050_rls_initplan.sql` have not been applied to the hosted project.

## How to run it

```
CRM_PERF=1 CRM_PERF_RUNS=2 npx vitest run tests/perf                      # full dataset, as measured below (about 22 minutes)
CRM_PERF=1 npx vitest run tests/perf                                      # 5 timed calls per measurement (about an hour)
CRM_PERF=1 CRM_PERF_SCALE=0.1 CRM_PERF_RUNS=1 npx vitest run tests/perf   # a tenth of the data, a few minutes
```

`vitest.config.ts` leaves `tests/perf/**` out of the default suite unless `CRM_PERF=1`. Other switches: `CRM_PERF_PHASE=<label>` prefixes the
phase names, `CRM_PERF_PROPOSAL=0` skips the phase with migration 0050 (row-level security once per statement), `CRM_PERF_RUNS_PROPOSED`
sets the timed calls in that phase, `CRM_PERF_STEPS=...` reorders the steps (`drop-0050`, `add-0050`, `drop-0038`, `add-0038`, `measure`;
`proposed-rls` is kept as another name for `add-0050`). The test database starts with every migration, so the default sequence rolls 0050
back first (`drop-0050,drop-0038,measure,add-0038,measure,add-0050,measure`). Each phase writes
`.data/perf/crm-scale-<phase>.json` (git-ignored): every measurement, the statements of the slowest call, the indexes each call scanned,
and the full `EXPLAIN (ANALYZE, BUFFERS)` text of each call's slowest read.

The always-on guard is `tests/crm-performance.test.ts` (seconds, default suite): the 0038 indexes exist with the definitions the queries
rely on and the planner picks them (both name orders included), the three measured-and-rejected candidates are absent, every list read
sends a bounded LIMIT whatever page size is asked for, a long conversation opens with its newest page of messages only, "has all" of 200
tags (and a filter of 40 such conditions) plans in milliseconds for contacts and companies, and the query rewrites below return the same
answers as before.

| File | What it is |
| --- | --- |
| `tests/perf/seed.ts` | The dataset: configuration through the real services, bulk rows through set-based SQL |
| `tests/perf/harness.ts` | Statement capture, timing, index scan counters, EXPLAIN in the original security context, fingerprints, report writer |
| `tests/perf/pairs.ts` | Each replaced statement next to its replacement, timed in the same phase |
| `tests/perf/crm-scale.perf.test.ts` | The scenarios and the phases |
| `tests/perf/rls-initplan.proposal.sql` | The row-level-security experiment the historical runs below call "proposed RLS"; superseded by 0050, no longer run |
| `supabase/migrations/0050_rls_initplan.sql` + `supabase/rollbacks/0050_rls_initplan.down.sql` | Row-level security once per statement, generated by `scripts/rls-initplan.ts`; see `docs/rls-performance-rollout.md` |
| `supabase/migrations/0038_crm_performance.sql` + `supabase/rollbacks/0038_crm_performance.down.sql` | The indexes and their rollback |

## Dataset

| Contacts (2% archived, 0.5% deleted) | 50,000 | 70,000 |
| Contact identities (every email and phone, plus a second email for 1 in 10) | 105,000 | 147,000 |
| Contact tags (10 common, 10 medium, 10 rare tags) | 63,182 | 88,454 |
| Custom field values (number, select, date, boolean, text) | 119,400 | 167,160 |
| Companies (40% of contacts linked) | 2,000 | 2,800 |
| Deals: 5,000 native over 3 pipelines (70/20/10%), open 70%, won 20%, lost 10%; plus 100 GoHighLevel cache rows | 5,100 | 7,300 |

The full 50,000-contact target from the brief fits: seeding takes 60 to 75 s; `ANALYZE` runs afterwards (hosted Postgres keeps statistics
current with autovacuum; PGlite does not).

## Method

Each scenario calls the real service function the screen uses (`listContacts`, `getBoard`, `listBookableSlots`, `getCrmReport`,
`listConversations`, ...) as a workspace owner, so member reads run under row-level security exactly as in the app. One warm-up call, then
timed calls; the tables show the median (2 timed calls per measurement, 5 in the proposed-policy phase). `capture` records every statement
each call sends (with its own time and whether it ran as the member or as trusted code), so a statement count that grows with the page size
would show an N+1; the slowest read is re-run with `EXPLAIN (ANALYZE, BUFFERS)` as the same member; and the `pg_stat_user_indexes` counters
are read before and after each scenario, so every index any of its statements scanned is recorded, not only the slowest statement's.

Phases run on the same data in one process: without the 0038 indexes, with them, and with them plus the row-level-security experiment.
Every call's result is fingerprinted (a hash of its JSON, ignoring clock-relative fields), and the suite fails if a phase returns anything
different for a compared call. Six calls are not compared because their answer moves while the suite runs (one saves a new list each time;
the others filter on `now()` inside SQL).

How to read it:

- **Row-level security dominates every member read** (finding 1 below). The same first page takes 22 ms as trusted code and 3.2 s as the
  owner; the index counters show about 244,000 permission lookups (`users_pkey`, `memberships_user_idx`, `role_permissions_pkey`) for that
  one 25-row page, against 51 with the proposed policies. The 90-day report makes about 1.3 million.
- **The reliable comparisons are inside one run**: 0038 off and on are consecutive phases on the same database, and the statement pairs
  below run in the same phase. "Before" was a separate run on a busier machine: calls whose SQL did not change at all (deals table, metrics
  strip, portal dashboard, CRM overview, inbox list) also came out 2.5 to 4 times slower there, so only differences well beyond that band
  are clearly the fixes': "has all of two tags" (22 s to about 1.2 s), the phone-digits search (97.5 s to 10.7 to 14.4 s, 7 to 9 times) and
  opening a conversation (834 ms to 10 ms). The name and email searches (52.6 s and 43.8 s to 9.9 to 22 s, 2.4 to 5.3 times) overlap the
  load band, so their cross-run figures say little. Their within-run evidence: the old search call made two full passes under row-level
  security (the page, then a separate count), the new one makes one. Timed in the same phase (run 3, statement pairs below), the old email
  search's page and count statements take 14.4 s + 16.0 s without 0038 and 15.5 s + 14.7 s with it, against 11.0 s and 10.7 s for the new
  single pass: about 2.8 times for the whole call. The count statements alone go from 13.9 s to 10.2 s (email) and 14.8 s to 10.9 s
  (phone) in run 2. Quote these within-run figures, not the cross-run ones.
- **What 0038 changes under today's policies**: directory pages (newest first or by name) go from 8 to 9 s to about 3.3 s (run 3, on a
  more loaded machine: newest first 7.0 s to 5.3 s, A to Z 7.0 s to 3.7 s, Z to A 7.6 s to 3.8 s; Z to A is what the Sort menu's first click
  on Name sends, and before `contacts_directory_name_desc_idx` it sorted the whole workspace even with 0038), the custom-field
  filters and the "no activity" list by 2.5 to 5 times, the isolation probes (another workspace's owner, the viewer) by 1.7 to 3.6 times,
  past appointments by about 10%. The reports did not use any 0038 index with today's policies (see the counters), so their 0038-off/on difference is machine load.
- **Machine load is visible in the trusted-code row**: with the same indexes, the same trusted call took 76 and 192 ms in the two runs
  without 0038, and 21 and 110 ms in the two proposed-policy phases (which have 0038). Run 1's proposed-policy phase ran under heavier
  machine load, so its numbers are 2 to 5 times run 2's. Read single cells as orders of magnitude.
- **No N+1**: statements per call are constant (5 for a contact page of 25 or 100 rows, 68 for every report section whatever the data, 11
  to open a conversation, 1 for the inbox list).

### Planning cost of "has all"

The first rewrite of "has all" (one `exists` per tag) was fast to run for two tags but its planning time grew faster than the square of the
tag count: PostgreSQL turns each `exists` into a semi-join, and every one of them joins on the contact's id. A condition takes up to 200
tag ids, which are only format-checked (they need not exist), and a filter takes up to 40 conditions, so any member who can view contacts
could send a filter that held a database connection planning for seconds or longer (the Contacts page `?f=`, a Smart List, the API, and
the same compiler serves workflow conditions, campaign audiences, assignment rules and company filters). Measured planning time
(`EXPLAIN (SUMMARY)`, PGlite, small workspace; planning does not depend on the data size):

| Filter | One `exists` per tag | Grouped sub-select (now) |
|---|---:|---:|
| has all of 4 / 8 / 16 / 32 / 64 tags | 3.8 / 31 / 55 / 153 / 687 ms | 0.3 to 1.8 ms at any count (2 to 200 tags) |
| has all of 100 tags (whole `listContacts` call) | 1.6 to 6.5 s planning, 12 to 25 s per call | 0.7 ms planning at 200 tags |
| has all of 200 tags | PGlite aborted after about 27 s | covered by the guard test, plans in milliseconds |
| 40 conditions of 2 / 3 / 4 tags each | 396 / 841 / 2,571 ms | 76 / 70 / 91 ms |

The last row is why the per-tag form is not kept even for a few tags: the cost adds up across conditions, so a cut-off on the tag count
per condition would still let 40 small conditions plan for seconds. Execution, on the full dataset in one run (owner under today's
policies / trusted code, best of two `EXPLAIN ANALYZE`, count statement):

| Tags | One `exists` per tag | Grouped sub-select |
|---|---:|---:|
| 2 | 554 ms / 12 ms | 492 ms / 16 ms |
| 3 | 402 ms / 5 ms | 710 ms / 18 ms |
| 4 | 404 ms / 5 ms | 1,012 ms / 26 ms |
| 8 | 692 ms / 9 ms (planning 18 to 45 ms) | 2,365 ms / 63 ms (planning 0.4 ms) |

For two tags (the measured screen) the grouped form is as fast or faster; for 3 to 8 tags it is up to about 3.5 times slower under
today's policies, because it reads every link of the named tags and each row pays the per-row policy call (finding 1). With the proposed
policies the difference is tens of milliseconds. A bounded plan is worth that.

### A long conversation

A probe opened one SMS conversation of 5,000 messages as the owner (PGlite, today's policies). Before the cap, the messages statement read
all 5,000 rows (sequential scan, 14 to 27 ms) and the detail would have been about 1.7 MB of JSON; now it reads the newest 201 backwards on
`conversation_messages_thread_idx` (2.2 to 2.5 ms), and the whole `getConversationDetail` call takes 25 to 49 ms and returns 200 messages,
`olderMessages`, and 77 KB. A thread over the cap makes one more statement (older drafts awaiting approval), so 12 instead of 11.

## Finding 1: row-level security costs more than everything else put together

Every member read runs under row-level security (`crmRead` uses `withUser`), and the policies call
`app.has_permission(org_id, '<permission>')` (or `app.can_view_conversation(...)`, `app.can_access_org(...)`) with the row's own `org_id`.
They are `SECURITY DEFINER` SQL functions, which PostgreSQL never inlines, so the function runs once for every row a statement reads, and
each call does several lookups of its own (`org_role`, `staff_assigned`, overrides, `role_permissions`). On the measured dataset that is
about 0.1 ms per row in PGlite: a count over the workspace's 50,000 contacts makes 50,000 calls (the counters above: about 244,000
permission lookups for one contact page and its total).

Two more effects follow from it:

- **The trigram index on `contacts.search_text` can never serve a member.** `LIKE` (`textlike`) is not leakproof, and PostgreSQL only uses
  a non-leakproof condition as an index condition when the table has no security policy for the role. Under row-level security every
  `%term%` search reads the workspace's contacts one by one. Equality and range comparisons on uuid, text, timestamptz, int, date and bool
  are leakproof, so the btree indexes in 0038 do work for members; comparisons on `numeric` are not, so a range filter on a custom number
  field cannot use an index for members either.
- **Plans pick hash joins that read whole tables.** The planner prices the policy function like any other filter, so it often reads all of
  a workspace's contacts (calling the function for each) to join them to a few hundred conversations.

The fix was first measured as an experiment (`tests/perf/rls-initplan.proposal.sql`, applied by the suite to its throwaway database
only, the "proposed RLS" column above): two helpers, `app.permitted_orgs(permission)` and `app.accessible_orgs()`, return the
organizations where the current user holds a permission (or has access), once per statement; each SELECT policy's per-row call is
rewritten to `org_id = ANY ((SELECT app.permitted_orgs('<permission>'))::uuid[])`. The sub-select is an InitPlan, evaluated once per
statement, and the comparison is a leakproof uuid test the planner can also use as an index condition. With it, every compared call
returned byte-for-byte the same result, including the isolation probes, and member timings dropped to the trusted-code timings. The
experiment rewrote 160 SELECT policies with a regular expression and missed one (`organizations_select`, `app.can_access_org(id)`).

### Final policy rewrite: migration 0050

`supabase/migrations/0050_rls_initplan.sql` (rollback `supabase/rollbacks/0050_rls_initplan.down.sql`) is the reviewed rewrite after
all earlier CRM, workforce and AQi policies are present. The proof, verification and hosted rollout are in
`docs/rls-performance-rollout.md`. In short:

- **Generated, explicit.** `scripts/rls-initplan.ts` reads `pg_policies` after every earlier migration and writes one checked
  `alter policy` per SELECT policy: 166 policies (178 calls: 162 `has_permission`, 15 `can_access_org`, 1 `can_view_conversation`),

- **Proven, not argued.** The final permission helpers include active-client scoping, agency-manager client scopes and support-session

- **Not applied to the hosted project.** Hosted schema reconciliation, a tested backup restore and the staging verifier are required

## Known limits and what is not done

- **Row-level security per row: fixed by 0050, not yet on the hosted project.** Migration 0050 (above, and
  `docs/rls-performance-rollout.md`) spells out each `alter policy`; until it is applied (with the user's approval), hosted member reads
  keep the per-row helper calls. The latency figures in the historical table above use the earlier 0040 model and are not estimates for
  0050. Still per row after 0050: `app.staff_assigned(org_id)` (18 SELECT policies, mostly after a rewritten check), `app.file_permission`
  (`org_files`), `app.shares_org_with` (`users`), the zero-argument `app.is_agency_admin()` / `app.is_agency_staff()`, and the policies for
  other commands; none is on the measured hot paths.
- **Totals are still exact counts.** A full page of an unfiltered directory, a smart list or a filter still counts every matching row
  (searches count in the same pass). An approximate or capped total ("10,000+") would be a product decision.
- **Text search cannot use an index for members** (`LIKE` is not leakproof; see finding 1), even with 0050. A rare term reads the
  workspace's contacts once (about 80 to 230 ms in the proposal phase). Digit matching on identities reads every identity of the workspace
  (now with one regular expression per value instead of a digits-only copy); a stored digits-only column with its own index would avoid
  that, but that is a schema change, not an index.
- **Numeric custom-field ranges** (`budget > 900000`) cannot use an index for members (`numeric` comparisons are not leakproof). They read
  the field's values, which is fast at this size.
- **The inbox list reads every visible conversation to sort it** (open escalations first, then priority, then recency, with the escalation
  coming from a lateral sub-select), 3,000 here: about 0.65 s with today's policies, about 30 ms with the proposal. A stored sort key would
  let it stop after the first 60; that is a schema change.
- **Older messages of a long conversation cannot be opened yet.** `getConversationDetail` now sends the newest 200 and sets
  `olderMessages` when there are more, but the inbox screen (`inbox-workspace.tsx`, owned elsewhere) neither says so nor offers a "load
  older messages" control; that control, and a service read of the page before `olderMessages.beforeId`, need the UI owner's agreement.
  The inbox page's delivery-event read (`withDeliveryDetail` in `src/app/(portal)/inbox/page.tsx`) still orders events oldest first under
  `limit 1000`; with at most about 250 messages that is about four events per message, and ordering it newest first would keep the newest
  messages' events if a thread ever exceeds that.
- **The calendar can return up to 2,000 appointments per window** (`SCHEDULE_LIMIT`); the screen says when the cap is reached.
- **The board still counts every deal of the pipeline** for the per-stage counts and totals (3,500 here), which is what the columns show.
- **Measured in PGlite only.** No hosted `EXPLAIN` was run (the hosted database is off limits). Hosted plans may differ: more organizations
  make `org_id` far more selective (PGlite with three workspaces sometimes prefers a sequential scan where hosted Postgres would use the
  index), and hosted may run an older major version than PGlite's 18.3.
- **Variance.** The machine ran other test suites at the same time. Identical calls in the two runs differ by up to about 5 times in some
  phases (the trusted-code row shows it), so read single cells as orders of magnitude; the statement pairs and the 0038-off/on phases inside
  one run are the reliable comparisons.
- **0038 was narrowed after an earlier draft** from nine indexes to six. A local database that applied the draft keeps the three unused
  ones (`crm_contact_tags_tag_contact_idx`, `crm_opportunities_board_order_idx`, `crm_external_busy_user_end_idx`); they are harmless, and
  can be dropped by hand or by recreating the local database. The hosted project never had either version.
- **0038 then gained `contacts_directory_name_desc_idx`** (after the review found the Sort menu's first click on Name sends Z to A). A
  local database that already recorded 0038 as applied does not get it, because the runner skips applied versions: run that one
  `create index if not exists` statement from the migration by hand, or recreate the local database. The hosted project has applied no
  version of 0038.
- **No statement timeout and no cap on the total number of values in a filter.** Each condition takes at most 200 values and a filter at
  most 40 conditions; "has all" no longer costs more to plan as the values grow, but nothing stops a slow statement in general.
  `statement_timeout` for the app's database role (or per transaction in `crmRead`) and a cap on the values across a whole filter in
  `parseFilter` (`src/lib/crm/filters.ts`) would be a cheap further defence; neither file is this package's.
