# Automation Studio: decisions only the founder can make

Each has a recommended default that the code already follows, so nothing is blocked; changing a default is a small edit.
Status as of 2026-10-21: items 1 to 4 and 7 were **decided by the founder** (below); the rest are still open or follow their default.

| # | Decision | What the code does now | Why it matters |
| --- | --- | --- | --- |
| 1 | **Is the existing CRM workflow builder core or premium?** (**Decided: core.** Premium Studio features need the active plan and are enforced at every API, mutation, execution, template and integration boundary.) | Core. Workflows built in the CRM screens (and every workflow that existed) need no plan and are never paused by the plan's lifecycle. Only workflows built in Automation Studio, and steps that only the plan includes, are premium. | The brief says the $299 plan must not be required for ordinary core CRM functionality, and also lists "native premium workflow creation and execution". The two readings differ for clients who already use `/crm/workflows`. If the CRM builder should become premium too, set `origin = 'studio'` for new CRM-screen workflows and decide what happens to existing ones (grandfather them is recommended). |
| 2 | **Fair-use defaults** (**Decided: stay configurable and provisional.**) | 5,000 runs, 50,000 steps, 300 builder messages, 500 employee requests, 10,000 integration calls per month; 25 workflows switched on; 500 runs in progress. Provisional. Hard stop on. | Real cost data (LLM tokens per builder message, connector costs) does not exist yet. Set these from the first month of measured usage. |
| 3 | **Grace period for a failed payment** (**Decided: keep 7 days as a configurable default, with clear client notifications.**) | 7 days default; `STUDIO_PAYMENT_GRACE_DAYS` (1 to 30) sets the platform default, and the agency member recording a failure can choose per case. The client is told the actual date, and again 48 hours before it ends. | Disclosed on the upgrade page. |
| 4 | **What a lapse keeps, and for how long** (**Decided: retain paused premium definitions while the workspace exists, subject to documented deletion and retention policies.**) | Everything is kept for as long as the workspace exists (definitions, versions, run history). Workflows are paused, in-progress runs wait. | The brief asks for "the disclosed retention policy"; none existed. Confirm this one or set a limit, then change `STUDIO_LAPSE_POLICY` and the sweeper together. |
| 5 | **Who verifies payment** | An agency member, by recording it (`recordVerifiedPayment`). | A recurring PayMongo (or other) subscription is not built (`docs/build-progress.md`). Without it the plan is only as automatic as the team's bookkeeping. |
| 6 | **Route and name** | `Automation Studio`, `automation-studio`. | "Studio" already means Website Studio in this repository. |
| 7 | **Canvas technology** (**Decided: `@xyflow/react`.**) | Installed at 12.12.0, pinned, reusing the canonical graph and operations layer. | Done. |
| 8 | **First connectors** (**Priority set: native CRM, webhooks/HTTP, Slack, Gmail, Google Sheets; audit existing infrastructure before building each.**) | Built in Phase C: HTTP request and Slack (incoming webhook) on tenant-scoped connections ([connections-and-outbound.md](connections-and-outbound.md)). Still missing, and needing the founder: a Slack app for OAuth, a Google OAuth app with Gmail and Sheets scopes. | Each needs credentials or an OAuth app registered by the founder (Google, Microsoft, Slack, Stripe). A generic HTTP-request step needs none and covers many cases. |
| 9 | **Scheduler activation** (**Decided: not until the `withinInterval` fix is integrated and verified, due-run claiming is multi-tenant safe, and controlled end-to-end tests pass.**) | Off in production. The fix is integrated (atomic per-job claim) and per-workspace fair claiming is in, both tested locally; the controlled end-to-end run has not been done. | Nothing here runs in production until it is turned on (`docs/production-scheduler.md`). |
| 10 | **Applying migrations `0069`, `0070`, `0071` and `0072`** | Not applied to any hosted database; all four are applied only to local and test databases. `0072` (connections) is new in Phase C; code that reads its tables checks that they exist, so it degrades to "no connections" if deployed first. | Apply them in order before deploying code that reads the new columns, tables and function (the portal shell calls `app.automation_studio_plan()` from `0071` on every page, so deploying the code first would break every page). The rollbacks are in `supabase/rollbacks/` (newest first); `0070` refuses to roll back while any conversation or change history exists. |
| 11 | **AI employee names in the brief** | Templates will use the six real roles. | "AI Lead Qualifier" and "AI Receptionist" do not exist. Adding roles is a separate piece of work that touches Hermes profiles. |
| 12 | **Should the agency review a new connection's host before it can be verified?** | No. A workspace owner or manager with the automations permission can add any public https host; the platform refuses private, local and non-https addresses, and every call is limited, logged and approved per version. | The safe default for a self-service product. If clients abuse it, add an agency allow- or deny-list on `automation_connections.settings.host` and check it in `createConnection` and `performOutbound`. |
| 13 | **Slack OAuth app** | Not built; Slack works through incoming webhooks. | Needs a Slack app registered by the founder (client id/secret, redirect URL, scopes `chat:write` and `channels:read`). Design is in [connections-and-outbound.md](connections-and-outbound.md). |
| 14 | **Outbound limits** | 5 calls in flight per workspace, 60 calls a minute per connection, 5 tests an hour per connection, 20 connections per workspace, 256 KB response, 16 KB body, 30 s timeout. Provisional, in code (`performOutbound`, `rate-limit.ts`, `HTTP_LIMITS`). | Tune from measured use; the monthly `integration_calls` limit is already per workspace and configurable. |
| 15 | **Payment provider for billing automation** | None. Payments are recorded by an agency member who confirms them in their own records; the product never says a payment was taken or detected. | Without a provider (PayMongo or other) the plan is only as automatic as the team's bookkeeping. |
