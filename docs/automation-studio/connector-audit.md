# Automation Studio: connector audit

First written 2026-10-21; updated the same day for Phase C (HTTP request and Slack are now built). The founder's priority order is native CRM,
webhooks / HTTP, Slack, Gmail, Google Sheets, with the instruction to audit what exists before building each.

## What exists and works today

| Connector | What is there | Where | Notes |
| --- | --- | --- | --- |
| Native CRM | Every CRM step: contacts, tags, tasks, notes, deals, stages, fields, assignment, messages from approved templates, review requests, notifications, appointments as triggers | `src/lib/crm/workflow/spec.ts`, `src/server/crm/workflows/executors.ts` | Core, not premium. The Studio builder and canvas use exactly these step kinds. |
| Outbound webhook (a step) | The `webhook` step posts a signed event for the workspace's own **registered** subscription (`subscriptionId`, `includeContact`) | `src/server/crm/webhooks.ts`, step `webhook` | Public https only, SSRF-guarded, encrypted signing secret, 8 attempts with backoff, unknown outcomes are not auto-retried, auto-disable after 25 failures, delivery log with redeliver. Needs owner approval as an outside effect. Unchanged. |
| Inbound webhook (a trigger) | A private URL per published workflow starts a run; the plan lapse answers 409 before anything is created | `src/server/crm/workflows/inbound.ts` | Rate limited; the address is generated by the server (the AI builder can't set it; the *Leads from another system* template generates one). |
| n8n | A step calls a verified agency-registered n8n mapping | step `n8n` | Core. Zapier and Make reach the platform through the same webhook and API paths. |
| AI employees | `ai_task` asks one of the six real roles | step `ai_task` | Live runs stay off until each role's tool inventory is verified. |
| Email, SMS, WhatsApp | `send_message` from approved templates, with consent, opt-out and quiet-hours checks | `src/server/messaging` | Not changed. |
| **HTTP request (a step)** | **New (Phase C).** A call through a workspace's own *connection*: fixed host, allowed methods, credentials by reference, pinned DNS, no redirects, size and time limits, idempotency key, redacted log | `src/server/automation-studio/outbound.ts`, `src/server/security/outbound-http.ts`, `pinned-https.ts` | Premium; owner approval of the exact version; metered as `integration_calls`. Full design and test evidence: [connections-and-outbound.md](connections-and-outbound.md). |
| **Slack (a step)** | **New (Phase C).** Posts to a channel through an incoming webhook stored as an encrypted connection | same | Premium; same controls. Slack OAuth is designed, not built. |

## What does not exist

| Wanted | Missing | What building it needs | Blocked on |
| --- | --- | --- | --- |
| **Slack OAuth** (channel picker, bot token) | A Slack app and its token handling | A new connection kind on the same table; `conversations.list` for the picker; rotation | A Slack app registered by the founder (client id/secret, redirect URL, scopes `chat:write`, `channels:read`). The incoming-webhook path covers the common need meanwhile. |
| **Gmail** | Reading or sending as the person's own Gmail | Google OAuth with Gmail scopes. The Google Calendar OAuth plumbing (`src/server/calendars/adapters/oauth.ts`) is reusable for the flow. Sending as the person would also have to go through the existing consent, opt-out and approval rules. | A Google Cloud OAuth app with the Gmail scopes. Gmail scopes are "restricted": Google requires app verification and a security assessment before production use. Founder-owned, with a lead time. |
| **Google Sheets** | Appending or reading rows | The same Google OAuth plumbing with a Sheets scope (sensitive: verification still required) | The same OAuth app and verification. Until then an HTTP connection to a service that exposes an API can write rows. |

## Rules every connector follows (enforced for the existing ones and for the two new ones)

- An outside effect needs the business owner's approval of the exact published version, and a change makes a new version needing approval again.
- Premium connectors are checked against the plan at publish, switch-on, run and test time, and are paused (never failed) on a lapse.
- Every call is metered (`integration_calls`) and counted against the fair-use limit; refusals are recorded with the reason.
- Secrets are stored encrypted, never returned to the browser, the AI builder or logs; the builder can only name a connection that exists in the workspace.
- Dry runs describe the call and send nothing. The only real call outside a workflow is a connection's own test, which needs an explicit confirmation.
