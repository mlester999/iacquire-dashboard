# Client-only Hermes runtime

This package builds an isolated Hermes runtime and the restricted worker from one immutable official Hermes image. It is staged for review only. The worker service is Compose-profile gated (`provisioner`) and iAcquireOS must remain `HERMES_PROVISIONER_ENABLED=false` until the runtime passes isolated acceptance and receives explicit production approval.

## Layout and trust boundaries

- `hermes_home` holds only the default runtime home and its gateway state.
- `client_profiles` holds only named client profiles at `/opt/data/profiles/<profile>`.
- `worker_home` is separate from the Hermes home. It holds the worker's recovery journal and audit log. The worker gets a secret-free `config.yaml` and the client-profile volume, but it does not mount the Hermes home or its `.env`.
- The Hermes API has no published host port. It is reachable by the worker over loopback and by the approved Cloudflare Tunnel only through `hermes_private`. The API listener uses its per-profile bearer key; the public application also uses its Cloudflare Access service token.
- The provisioner process runs as UID/GID 10000 with a read-only root filesystem, no Linux capabilities, no Docker socket, and only explicit config/secret mounts plus the dedicated named volumes. The Hermes image uses its supported root-started s6 bootstrap to initialize the data volume, then runs the gateway as UID 10000. The gateway now has a read-only image filesystem, executable `/run` tmpfs for s6, non-executable `/tmp`, `no-new-privileges`, and only `CHOWN`, `KILL`, `SETGID`, and `SETUID` capabilities for volume ownership and supervised process handling. It has no host root, privileged mode, host PID/network mode, or host data directory.
- All direct messages, chat-platform adapters, and client communication credentials must remain disabled in this client runtime. Do not attach the agency data volume or any existing iAcquire profile.

The profile root and routing follow Hermes' documented layout: the default profile uses the Hermes home directly, named profiles live under `profiles/<name>`, and named API calls use `/p/<profile>/...` with that profile's own `API_SERVER_KEY`. Only the default profile starts the API listener; named profiles store their scoped keys but do not enable a second listener. The same gateway multiplexes profiles, but the portal still verifies each profile separately. See the [Hermes profile guide](https://hermes-agent.nousresearch.com/docs/user-guide/multi-profile-gateways) and [Docker guide](https://hermes-agent.nousresearch.com/docs/user-guide/docker).

The Dockerfile now requires both Hermes v0.22.5 and Node.js v26.12.1. The upstream v0.22.5 API server still does not register `/v1/tools`; `catalog-overlay-v0225` adds the narrow authenticated route using the current Hermes model-tool resolver. The upstream hashes were compared against the official v0.22.5 source and match; `SHA256SUMS` pins the reviewed patch. The Docker build checks the version, both checksum sets, Python compilation, and imports. GitHub Actions run [#76](https://github.com/mlester999/iacquire-dashboard/actions/runs/40259373467) built and exercised the pinned candidate with two synthetic tenants, twelve unique profiles and keys, SOUL canaries, config sync, tenant/key denials, recovery, idempotency, and cleanup. This is isolated sandbox acceptance only; local Docker remains unavailable, and no Hostinger client runtime has been installed.

The currently running production container is still Hermes v0.21.5. Its installed api_server.py, model_tools.py, and catalog helper SHA-256 values match the existing reviewed v0.21.5 overlay in this repository. This proves source parity only; no live API key was read and no authenticated inventory request was made. The v0.22.5 overlay remains an isolated acceptance candidate and is not a production upgrade authorization.

## Startup inventory gate

Before writing worker heartbeat/audit state or claiming a job, startup performs two authenticated reads of the default profile's complete catalog. The native contract, complete=true, explicit safe allowlist, exact toolsets, tool provenance and names, challenge echo, optional HMAC, and stable digest are required. Each read has a distinct challenge, a cache-busting query value, and no-store headers. An absent or unadvertised route, missing metadata, unsafe tools, invalid HMAC, or changing catalog exits before any job is claimed. Each new or synchronized client profile is checked again with its own key before a success callback.

## Private files

Keep all files outside the repository and out of Compose environment values and logs. On the Linux host, the secret-free Hermes config and bootstrap API key are shared with the restricted-root gateway, so they must be regular files owned by `root:10000` with mode `0440`. Worker-only secret files must be regular files owned by UID `10000` and mode `0400` or `0600`.

1. Copy `client-config.yaml.example` to a private deployment path. Replace the model identifier with a reviewed value supported by the pinned Hermes build. Keep credentials out of YAML; the worker refuses secret-looking model fields. The same secret-free config is mounted into Hermes and the worker. Set ownership to `root:10000` and mode `0440` so restricted-root Hermes and the worker's group can read it.
2. Create `hermes-api-key` as exactly 64 lowercase hexadecimal characters. This key is used only for the default profile's read-only startup inventory probe. The Hermes API wrapper reads it from a mounted file and keeps it out of Docker's declared environment. Set ownership to `root:10000` and mode `0440`; the worker accepts only this exact shared-file policy or a worker-owned `0400`/`0600` file.
3. Create `profile-model-env.json` with exactly `schemaVersion`, `environment`, and `value`, for example `{"schemaVersion":1,"environment":"OPENAI_API_KEY","value":"<secret>"}`. Keep it worker-only, owned by UID `10000` and mode `0400` or `0600`. The environment name must be one of the explicit model-provider API-key names supported by the worker; bot, CRM, customer, messaging and Hermes API key names are rejected. The worker copies this one approved model-provider key into each client profile's private `.env`, because Hermes resolves provider keys from the owning profile rather than falling back to another profile. The value is never returned to iAcquireOS or written to audit logs.
4. Create `provisioner-token` with the same dedicated random token configured server-side as `HERMES_PROVISIONER_TOKEN`. Keep it worker-only, owned by UID `10000` and mode `0400` or `0600`. Pin the matching `HERMES_PROVISIONER_GATEWAY_ID` on iAcquireOS and in the Compose env file. The token is bound to one gateway and is not a Docker or SSH credential.
5. Copy `client.env.example` to a private Compose env file and replace its placeholders. The production application also needs an approved exact HTTPS hostname in `INTEGRATION_ALLOWED_HOSTS`, a Cloudflare Access service-token credential in Vault, and a Cloudflare Tunnel route into the private network. Do not open port 8642 on the VPS firewall or publish it in Compose.

For example, an operator can create key files locally using a secret manager or an approved secure shell. Never enable shell tracing. Before using a profile-model secret, review which model provider's key format and environment name the selected Hermes version supports.

## Resource and health limits

The initial acceptance caps are 1 CPU and 2 GiB for Hermes and 0.5 CPU and 512 MiB for the worker; the API server is limited to one concurrent run. These caps are starting limits for the verified KVM 2 host, not a load-tested production capacity claim. The Hermes container health check reads `/health`; the worker health check requires a fresh private heartbeat. Both services rotate container logs. The JSONL worker audit remains mode `0600` on the persistent worker volume and fails closed if it cannot be written.

## Rollback

Keep the client-only volumes and last known image digest. Stop only the client Hermes and provisioner services; do not stop or recreate the agency Hermes app. Revert the portal application separately, leave the provisioner disabled, and retain the job/audit history. Do not delete `client_profiles` or `worker_home` while any client profile mapping or sync history exists. Restore a prior client-only image by digest only after confirming its on-disk config compatibility. Database rollback is governed by `supabase/rollbacks/0084_restricted_hermes_provisioner.down.sql` and must not discard sync history.

No Hostinger client service has been installed, no production named volume has been created, no database has been migrated, and no production profile has been created. The 12 synthetic profiles created during GitHub Actions acceptance existed only on the disposable hosted runner and were removed during job teardown.
